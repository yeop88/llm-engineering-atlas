# 데이터 처리 — 수집 · 전처리 · 평가 자료 기록과 유효하게 처리하는 법

이 앱에서 데이터가 들어와 검색 · 평가에 쓰이기까지 **무엇을 어떻게 처리했는지**와, 그 결과를 믿을 수 있게 하려면 **무엇을 지켜야 하는지**를 한곳에 남깁니다. 데이터 처리(수집 · 정제 · 청킹 · 색인 · 평가 질문)를 바꾸면 이 문서를 함께 고칩니다.

```
수집(업로드 · 공개 자료) → 정제 · 조립 → 문서 저장(중복 제거) → 청킹 → 형태소 토큰 → 임베딩 색인
                                                         └→ 평가 질문 생성(누수 방지) → 검토 → 평가 세트
```

## 1. 수집

### 1-1. 직접 올리는 문서

| 형식 | 처리 | 주의 |
|---|---|---|
| HWP 5.x · HWPX | 바이너리 · XML 구조를 직접 읽음(외부 프로그램 없음), 구역 단위로 보관 | 배포용(보호) HWP 는 미리보기 텍스트만, 암호 문서 불가. 표는 셀이 줄 단위로 |
| PDF | 쪽 단위 추출 | 스캔 PDF 는 글자가 없어 OCR 필요(업로드 시 경고). 목차 점선 · 머리말 · 쪽 번호가 섞임 |
| DOCX | 문단 · 표(셀을 ` \| ` 로 이음) | |
| TXT · MD · HTML · CSV · TSV · JSON · JSONL | 텍스트로 | HTML 은 태그 제거 |
| 이미지 · 영상 | 원본 저장, 영상은 2초 간격 프레임 중 화면이 거의 같은 것은 버림(16×16 흑백 평균 차 < 6) | 이미지 1장 · 프레임 1장 = 청크 1개 |

- 파일당 최대 `MAX_UPLOAD_MB`(기본 100MB).
- **같은 내용(SHA-256)은 같은 컬렉션에 한 번만** 들어갑니다. 실측에서 Windows 배경 사진 2쌍이 이름만 다른 같은 파일이었고 자동으로 걸러졌습니다.

### 1-2. 공개 자료 (프리셋)

현재 프리셋은 **'근로 · 주택임대차 법령과 판례'**(`labor_lease_law`, `app/stages/rag/public_corpus.py`)입니다.

| 단계 | 처리 | 이유 |
|---|---|---|
| 출처 | 법령: 국가법령정보 → HF `smhilee/korean-law-dataset`(공공누리 제1유형, 157개 JSONL · 약 480MB). 판례: 법원 판례 공개 → HF `joonhok-exo-ai/korean_law_open_data_precedents`(openrail, 5개 Parquet · 약 490MB, 171,599건) | 법령 · 판결은 저작권법 제7조의 비보호 저작물. 데이터셋 라이선스를 문서마다 기록 |
| 내려받기 | 원본 파일을 `data/public/` 에 한 번만 받음(크기가 같으면 건너뜀) | 데이터셋 서버의 조건 조회 · 검색 API 는 실측 당시 '생성 실패 · 인증 시간 초과' 오류가 잦았음. 원본을 받아 로컬에서 거르면 재현됨 |
| 법령 거르기 | 법령명이 근로기준법 · 동 시행령 · 최저임금법 · 동 시행령 · 주택임대차보호법 · 동 시행령인 행 | 파일이 법령명 순이 아니라 157개 파일을 모두 훑음(문자열로 먼저 거른 뒤 JSON 파싱 — 빠르게) |
| 판례 거르기 | 대법원 판결 · 참조조문에 세 법령 중 하나가 있음 · 판결요지가 비어 있지 않음 → 최근 선고순 · 법령별 같은 수(최대 240 ÷ 3 = 80) | 하급심은 사실관계 위주라 일반화된 판단(요지)이 적음. 요지가 없으면 질문의 근거가 약함. 최근 판례가 현행법과 맞을 가능성이 큼 |
| 법령 조립 | 법령 하나 = 문서 하나, `제N조(제목)` · `① 항` · `1. 호` 줄로. 조문번호 순 정렬 | 법률 구조 청킹이 '제N조'를 경계로 자르게 |
| 판례 조립 | 판례 하나 = 문서 하나, 첫 줄 사건명 · 법원 · 선고일 · 사건번호 + 【판시사항】【판결요지】【참조조문】【참조판례】 + 【전문】 앞 4,000자 | 전문은 수만 자라 전부 넣으면 색인 · 질문 생성 비용이 커지고, 핵심(쟁점 · 결론)은 판시사항 · 요지에 있음 |
| 파일 이름 | `판례 {사건번호} {사건명}` 에서 `\ / : * ? " < > \|` 를 `_` 로, 120자에서 자름 | 운영체제 파일 이름 규칙 |
| 출처 기록 | 문서 `meta.source` = 데이터셋 · 라이선스 · 종류(statute · precedent) · 사건번호 · 원본 id | 재현과 라이선스 확인 |

## 2. 정제 · 조립에서 발견한 문제와 처리

| 문제 | 발견 | 처리 |
|---|---|---|
| **법령 조문 머리 · 항이 호마다 반복** | 원본이 '호' 하나가 한 행이라, 그대로 이으면 제2조 머리가 9번 반복됨(근로기준법 51,072자) | 직전에 쓴 조문 · 항과 같으면 다시 쓰지 않음 → 37,455자. 반복 글은 청크를 같은 내용으로 채우고 BM25 · 임베딩 점수를 왜곡함 |
| **판례 분포 치우침** | 최저임금법을 인용한 대법원 판례가 4건뿐이라 법령별 80건 할당이 채워지지 않음 | 그대로 둠(없는 자료를 만들 수 없음). 질문도 최저임금 쪽이 적어 **법령별 결과를 따로 볼 때 최저임금은 표본이 작다**는 점에 주의 |
| **여러 법령을 인용한 판례의 분류** | 참조조문에 두 법령이 다 있으면 목록 앞 법령(근로기준법)으로 셈 | 할당 계산에만 쓰이고 문서 내용에는 영향 없음 |
| **짧은 청크가 많음** | 법률 구조 청킹이 조문 · 구획 단위로 잘라 100자 이하 청크가 35%(2,762개 중 976개, 중앙값 244자). 짧은 조문 · 【참조조문】 같은 짧은 구획이 그대로 한 청크 | 청킹 옵션 **짧은 청크 합치기**(`merge_below`)를 추가 — 기준보다 짧은 청크를 이웃 조문 · 구획과 크기 한도 안에서 합침(원문 구간으로 다시 잘라 겹침 중복 없음, 제목은 '제N조 외'). 200자로 하면 2,762 → 1,613청크, 100자 이하 976 → 24개. 검색 품질 차이는 같은 평가 세트로 재서 기록할 것 |
| **최소 길이 필터로 빠지는 청크** | 최소 길이(기본 20자) 미만 청크 151개가 빠짐(2,913 → 2,762) — 대부분 **삭제된 조문**('제35조 삭제 <2019.1.15>')과 내용 없는 구획 머리(【참조판례】만 있는 줄 · 당사자 표시) | 대체로 유익(삭제 조문은 답이 될 수 없음). 다만 '제2조의2' 처럼 제목만 남은 조문도 빠지므로, 합치기를 켜면 짧은 조각이 이웃과 합쳐져 버려지지 않음 |
| 판례 전문 자르기 | 4,000자 이후 '…(이하 생략)' | 전문 뒷부분(이유의 세부)에 근거가 있는 질문은 만들 수 없음 — 질문 생성도 같은 문서에서 하므로 평가가 왜곡되지는 않음 |

## 3. 청킹 · 토큰 · 색인

| 단계 | 처리 | 이유 |
|---|---|---|
| 청킹 | 전략 5종(재귀 · 고정 · 문장 · **법률 구조** · 페이지). 법률 자료는 '법률 구조'(800자 이하, 조문 · 항 · 판결문 구획 경계) | 조문 · 구획 단위로 잘라야 근거가 한 청크에 온전히 들어감 |
| 짧은 청크 합치기 | `merge_below` 보다 짧은 청크를 이웃과 합침(0 = 끔) | 문맥이 모자란 짧은 청크가 검색 결과 자리만 차지하는 것을 막음 |
| 최소 길이 | `min_chars`(기본 20) 미만 청크는 버림 | 삭제 조문 · 빈 구획 머리 같은 잡음 제거 |
| 청크 세트 | 원문(쪽 · 구역)을 보관하므로 전략을 바꿔 언제든 다시 나눔. 청크 수 · 길이 분포를 기록 | 같은 문서로 청킹 전략을 비교 |
| 형태소 토큰 | Kiwi 로 명사 · 동사 어간 등만 남겨 BM25 에 씀 | 한국어는 띄어쓰기 단위로 자르면 조사가 붙어 일치가 안 됨 |
| 임베딩 텍스트 | 청크 앞에 문서 제목 · 조문 제목을 붙여 인코딩(`include_title`) | 짧은 항 · 호 청크도 어느 법 · 어느 조문인지 알게 |
| 색인 | 문서 역할 프롬프트로 인코딩 · 정규화, 저장소별 코사인. 2만 개 이하 인덱스는 정확 검색 | MariaDB HNSW 의 기본 탐색 폭에서 문서 청크 묶음을 통째로 놓친 사고(재현율 0.79) 이후의 정책 |

## 4. 평가 질문 생성

| 단계 | 처리 | 이유 |
|---|---|---|
| 지문 고르기 | 문서마다 골고루(라운드 로빈) 무작위, 최소 글자 수(기본 200) 이상, 시드 고정 | 한 문서에 질문이 몰리지 않게 · 재현 |
| 적은 종류 보충 | `document_ids` 로 특정 문서에서만 지문을 뽑아 보충 세트 생성 | 문서 수가 적은 종류(법령 6 vs 판례 164)는 무작위로 거의 안 뽑힘 |
| 유형 | 사실 확인 · 다른 표현 · 상황 설명 · 조건 · 계산 · 긴 상황 설명 · 여러 문서 · 답 없음 ([rag.md](../stages/2-rag/rag.md#5-평가-세트)) | 쉬운 질문만 있으면 라우팅 · 에이전트 · 리랭킹의 차이가 안 보임(24문항 실측의 교훈) |
| 근거 문장 | LLM 이 지문 문장을 그대로 복사, 다르면 가장 많이 겹치는 문장으로 보정하고 '보정' 표시 | 청크 id 대신 근거 글로 정답을 기록해 청킹이 달라도 같은 세트로 평가 |
| 여러 문서 | 서로 다른 문서에서 글자 3-gram 자카드 ≥ 0.06 인 지문 쌍만 | 아무 두 지문이나 붙이면 억지 질문 |
| 답 없음 | 지문과 같은 주제의 빈칸을 묻게 함 | 그 지문에 답이 없다는 것만 보장 — 다른 문서에 답이 있을 수 있어 검토 필요 |
| 중복 · 겹침 | 같은 질문 제거, 질문-근거 어휘 겹침(글자 3-gram 자카드) 계산 | 겹침이 높으면 키워드 검색에 유리한 쉬운 세트 |

## 5. 학습 데이터 누수 방지

- 파인튜닝 · 증류 · LLM 증류 데이터는 **평가 세트의 근거 문장이 든 지문을 학습에서 뺍니다**(여러 문서 질문은 근거 모두). 비교에 쓰는 평가 세트는 자동으로 제외 목록에 들어갑니다.
- LLM 증류 데이터의 질문은 평가 세트가 아니라 지문에서 새로 만듭니다.

## 6. 유효하게 처리하기 — 점검 목록

**수집**
- [ ] 출처 · 라이선스를 문서마다 남겼는가 (재배포 여부와 별개로 사용 근거)
- [ ] 개인정보가 섞이지 않았는가 (판례는 법원이 비식별 처리한 공개본만)
- [ ] 거르기 기준(법원 · 기간 · 참조 법령 · 필수 필드)을 코드 · 문서에 남겼는가, 단계별로 몇 건이 남았는가

**정제**
- [ ] 원본 구조 때문에 생긴 반복 · 잡음(머리말 · 목차 · 반복 행)을 실제 텍스트를 열어 확인했는가 — 통계만 보면 못 찾음(법령 반복 사례)
- [ ] 중복(같은 파일)과 거의 같은 문서(개정 전후판 등)를 확인했는가
- [ ] 자르기(전문 4,000자 등)가 질문 · 근거 범위와 맞는가

**청킹 · 색인**
- [ ] 청크 길이 분포(중앙값 · 짧은 청크 비율)를 봤는가
- [ ] 근거 문장이 청크 경계에서 잘리는 비율은 — 평가에서 '근거를 담은 청크'가 없으면 그 질문은 어느 설정도 못 맞힘
- [ ] 작은 인덱스는 정확 검색인가 (근사 검색이면 재현율부터 확인)

**평가 세트**
- [ ] 질문 수가 비교에 충분한가 — 24문항에서는 대부분 '차이 불확실'이었다. 차이 2%p 를 가르려면 수백 문항
- [ ] 유형 · 문서 · 분야가 고르게 섞였는가 (최저임금법처럼 표본이 작은 분야는 따로 해석하지 않는다) — 문서 **종류**(법령 · 판례)별 지문 수도 센다
- [ ] 근거가 원문(청크)에 글자 그대로 있는가 — 생성 LLM 이 근거를 고치거나 줄인다(법률 세트 6%). 보정은 엄격한 기준으로만, 애매하면 질문을 뺀다
- [ ] 검토에서 이상한 질문(지문 없이 이해 안 됨 · 답이 지문에 없음 · 답 없음 질문인데 다른 문서에 답이 있음)을 걸렀는가
- [ ] 문장을 그대로 베낀 질문(문장 추출)으로만 평가하지 않는가 — 키워드 검색을 과대평가함
- [ ] 학습에 쓴 지문이 평가 근거와 겹치지 않는가 (누수)

**측정**
- [ ] 비교하는 설정끼리 같은 질문 · 같은 근거 · 같은 캐시 조건인가 (프롬프트 캐시로 한 쪽만 빨라 보인 사례)
