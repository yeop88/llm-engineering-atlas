# AI 엔지니어링 로드맵

임베딩 · RAG 검색 · 파인튜닝이 모델의 **지식**(파라미터에 담긴 기억과 외부 문서 기억)을 다룬다면, 리랭킹 · 에이전트 · 양자화 · 라우팅은 이를 실제 서비스에서 **적은 비용으로 빠르고 정확하게** 돌리기 위한 시스템 구성 요소(RAGOps / AI 엔지니어링)입니다.

다른 맵이 따로 있습니다 — [지식 그래프 · GraphRAG](kg-map.md), [멀티에이전트 · 멀티모달](agents-map.md), [평가 · 관측](maps/evalops.md), [보안 · 가드레일](maps/guardrails.md), [문서 처리](maps/docintel.md), [서빙 · 최적화](maps/serving.md), [대화 · 메모리](maps/conversation.md), [고객 AS 상담 시나리오](maps/as-service.md), [후학습](maps/posttrain.md). 전체 목록은 [문서 색인](README.md).

앱의 **맵**(`/roadmap`)과 단계 소개(`/stages/<단계>`)에 같은 내용이 있습니다. 화면 문구는 단계 레지스트리(`app/stages/registry.py`) 한 곳에서 만들어지므로, 단계를 진행하면 레지스트리의 상태 · 화면 · 할 일을 고칩니다. 아래 항목 중 '예정'인 것은 진행할 때 테스트 화면이 생깁니다.

## 전체 흐름

```
[데이터 임베딩] → [RAG 검색] → [리랭킹 (정밀 필터링)]
                                        ↓
[라우팅 (난이도 분류)] → 1) 쉬운 질문:  [지식 증류 · 양자화된 소형 모델] 이 처리
                       → 2) 어려운 질문: [파인튜닝 · 강화학습된 에이전트 LLM] 이 처리
```

| 단계 | 상태 |
|---|---|
| 데이터 임베딩 · 모델 비교 | 구현됨 (임베딩 테스트) |
| RAG 검색 · 평가 · 답변 생성 | 구현됨 (RAG 테스트) |
| 파인튜닝 | 구현됨 (파인튜닝 테스트, [finetune.md](stages/5-finetune/finetune.md)) |
| 검색 향상 (질의 재작성 · HyDE · 다중 질의) | 구현됨 (검색 향상 테스트, [search-lab.md](stages/4-search-lab/search-lab.md)) — 검색 설정 `enhance` 로 RAG 검색 · 평가 · 답변 어디서든 켬 |
| 리랭킹 | 구현됨 (리랭킹 테스트, [rerank.md](stages/3-rerank/rerank.md)) — LLM 목록형 · 융합 · 후보 수 곡선. 이전: 기초 있음 — 검색 재정렬 · 조합 평가에서 리랭커 선택. 고도화 예정 |
| 라우팅 | 구현됨 (라우팅 테스트, [routing.md](stages/6-routing/routing.md)) — 규칙 · 검색 확신도 · LLM 판단 라우터, 연결 실행에서도 사용 |

| 지식 증류 | 구현됨 (지식 증류 테스트, [distill.md](stages/7a-distill/distill.md)) |

| 강화학습 | 구현됨 (강화학습 테스트, [rl.md](stages/8b-rl/rl.md)) — 보상 · Best-of-N · 선호 쌍 · DPO 데이터 |

## 리랭킹 (Re-ranking)

1단계 검색(빠르지만 거친 벡터 · BM25)이 고른 후보를, 질문과 문서를 함께 읽는 크로스 인코더로 다시 줄 세워 정확도를 올립니다.

- 지금: 검색 비교 · 조합 평가에서 리랭커 11종을 고를 수 있습니다. CPU 에서는 후보 10개 재정렬에 질문당 약 22초가 걸렸습니다([rag.md](stages/2-rag/rag.md#6-조합-평가)).
- 할 일: 리랭커 전용 벤치마크와 후보 수(top-k) · 지연 곡선, LLM 리랭커(목록형 재정렬)와 크로스 인코더 비교, 양자화 · ONNX 로 속도 개선 후 재측정.

## 에이전틱 AI (LLM Agents)

LLM 이 한 번 검색하고 답하는 대신, 스스로 계획을 세워 검색을 여러 번 하고 도구(계산 · DB 조회 · 문서 열람)를 써서 복잡한 질문을 풉니다.

- 할 일: 질문 분해 → 여러 번 검색 → 근거 종합(다단계 RAG), 도구 호출(문서 필터 · 조문 조회 · 계산기), 단계별 기록과 비용 · 시간 측정, 평가 세트로 단일 검색 RAG 와 정답률 비교.

## 강화학습 (RL)

정답 근거 인용 · 사용자 피드백 같은 보상 신호로 모델의 행동(검색 방법 · 답변 방식)을 최적화합니다.

- 할 일: 보상 설계(근거 인용 정확도 · 환각 없음 · 답변 길이), 선호 데이터(좋은 답 / 나쁜 답) 수집 화면, DPO 등 선호 학습으로 소형 LLM 조정, 학습 전후 답변 평가 지표 비교.

## 지식 증류 (Distillation)

큰 모델(교사)의 판단을 작은 모델(학생)이 따라 하도록 학습시켜 비슷한 품질을 훨씬 적은 비용으로 냅니다.

- 할 일: 큰 임베딩 모델 → 작은 모델 벡터 증류, 크로스 인코더 점수 → 임베딩 모델 증류, 큰 LLM 답변 → 소형 LLM 학습 데이터, 크기 · 속도 · 정확도 3축 비교표.

## 양자화 (Quantization)

가중치 · 벡터를 낮은 정밀도(int8 · 4bit · binary)로 바꿔 메모리와 지연을 줄이고 정확도 손실을 잽니다.

- 할 일: 임베딩 벡터 int8 · binary 양자화와 재점수(rescoring), 모델 양자화(ONNX · OpenVINO · int8)로 인코딩 속도, LLM GGUF 비트 수(4 · 5 · 8bit)별 답변 품질 · 속도, 벡터 DB 용량 · 검색 지연 비교.

## 라우팅 (Model Routing)

질문의 난이도 · 종류를 먼저 분류해, 쉬운 질문은 작고 빠른 모델이, 어려운 질문은 크고 정확한 모델이 처리하게 나눕니다.

- 지금: 규칙 · 검색 확신도 · LLM 판단 라우터로 빠른 경로 / 전체 경로를 고르고, 평가 세트로 항상 빠른 · 항상 전체 · 오라클(상한)과 비용-품질을 비교합니다([routing.md](stages/6-routing/routing.md)). 7 · 8 이 없어 지금은 두 경로가 같은 LLM 을 쓰고 검색 단계(향상 · 리랭커)가 다릅니다.
- 할 일: 7 소형 모델이 생기면 빠른 경로의 답변 모델 교체, 임베딩 분류기 라우터(라벨 = 오라클 판단), 질문 수를 늘려 재측정.

## 연결 실행 — 부분 연결 · 전체 연결

맵 화면(`/roadmap`) 아래 **연결 실행**에서 단계들을 서비스 순서대로 이어 한 질문을 처리하고, 평가 세트로 연결 방식을 비교합니다. 코드는 `app/pipeline/flow.py`(실행기) · `app/pipeline/api.py`(`/api/flow/*`)입니다.

```
질문 → 4 질의 다듬기 → 1 질의 임베딩 → 2 검색 → 3 재정렬 → 6 난이도 분류 → 7·8 답변 모델 선택 → 2 답변 · 근거 검증
```

- 단계마다 **실행 / 꺼짐 / 기본 동작**과 걸린 시간을 남깁니다. 6 라우팅을 켜면 위의 향상 · 리랭커는 어려운 질문에만 쓰고, 연결 비교에는 어려움으로 보낸 비율이 함께 나옵니다. 아직 만들지 않은 단계(7 증류 · 양자화, 8 에이전트 · 강화학습)는 흐름에서 빼지 않고 '기본 동작'(모든 질문 → 기본 LLM)으로 지나갑니다. 흐름 전체를 지금 돌려 볼 수 있고, 단계를 구현하면 그 자리만 바꾸면 됩니다.
- 검색 부분(4 → 1 → 2 → 3)은 검색 연결점(`run_search`) 한 번으로 실행하고, 단계별 시간은 검색이 돌려주는 시간 기록을 단계에 나눠 담습니다. 단계마다 따로 부르면 검색 경로가 둘이 되어 결과가 어긋날 수 있어서입니다.
- 빠른 선택: `1→2 검색만` · `1→2→답변` · `4→1→2→답변` · `전체`. 평가 세트 비교는 첫 번째 연결을 기준으로 nDCG 짝지은 비교를 하고, 답변 지표(답변률 · 근거 인용 · 문장 근거율)와 단계별 평균 지연 막대를 함께 보여 줍니다.

### 실측 #1 · 2026-10-18 · 공공문서 · 직접 작성 24문항 중 10문항 (run #227)

읽은 것

- **단계를 더 이을수록 좋아지지는 않았습니다.** 다중 질의는 검색을 조금 올렸지만(+2.0%p, 불확실) 지연이 6초 늘었고, 리랭커는 1위 정답을 오히려 끌어내려(Hit@1 80 → 50) nDCG 를 12%p 떨어뜨렸습니다(10문항이라 불확실).
- 그런데도 **전체 연결의 답변 품질이 가장 좋았습니다**(근거 인용 80 → 100%, 문장 근거율 80 → 85%). 정답 근거가 1위가 아니어도 상위 5개 안에 있으면(Hit@5 100%) LLM 은 찾아 인용합니다. 답변 서비스에서는 1위 정확도(nDCG)보다 **상위 k 개 안에 근거가 들었는가**가 더 중요할 수 있다는 뜻입니다 — 검색 지표만 보고 단계를 빼면 안 되는 이유.
- 비용은 거의 전부 **LLM 답변(26~31초)과 CPU 리랭커(22초)** 입니다. 검색 자체는 0.2초. 그래서 다음 단계의 우선순위는 6 라우팅(쉬운 질문은 리랭커 · 큰 모델 없이)과 7 양자화 · 증류(답변 · 리랭커를 싸게)입니다 — 맵의 다음 단계와 일치합니다.
- 한계: 10문항 · 문서 4건으로 작아 모든 차이가 '불확실'입니다. 질문 수를 늘리고, GPU 에서 리랭커 지연을 다시 재야 합니다.
