# 적은 메모리로 큰 모델 — GGUF 머리말 · 메모리 계획 · 층 단위 스트리밍 · 전문가 오프로드 · 페이지 KV · 연속 배칭 · 극저비트 · 여러 기기 · 실측 (BM1~BM7)

화면은 `/bigmodel/plan`(메모리 계획 · 배치) · `/bigmodel/serve`(여러 요청 나눠 쓰기) · `/bigmodel/lab`(저비트 · 여러 기기), 코드는 `app/stages/bigmodel/` 입니다. 계산(계획 · 페이지 KV · 배칭 흉내 · 여러 기기 · 전문가 쓰임 흉내)은 바로 답하고, 모델을 올리거나 서버를 띄우는 실측은 작업으로 돌립니다. 서버 실측에는 `LLAMA_SERVER_BIN`, GGUF 는 `LLM_MODELS_DIR` 안의 파일 이름으로만 고릅니다.

```
GGUF 머리말 / HF config.json → 텐서별 바이트 · 층별 K · V 차원 (BM1)
  → 가중치 + KV(슬라이딩 창 · KV 공유 · 고정 상태) + 계산 버퍼
  → 배치 후보: 전부 GPU · 층 N 개 GPU · 전문가만 CPU · 앞 N 층 전문가만 CPU · 전부 CPU · 디스크 스트리밍
  → 장치별 메모리 · 들어가나 · 지붕선 토큰/초 · llama-server 인자
층 단위 스트리밍: 층마다 파일 → 뼈대(meta) + 층 하나씩 붙였다 떼기 + 미리 읽기 → 통째와 같은 답인지 (BM2)
배치 실측: 인자마다 서버 → 토큰/초 · 메모리 / 전문가 쓰임 → GPU 에 일부만 둘 때 적중률 (BM3)
여러 요청: 블록 단위 KV · 앞부분 공유 (BM4) · 걸음마다 넣는 연속 배칭 (BM5)
더 작게 · 더 넓게: 2비트 이하 · 삼진 품질 절벽 (BM6) · 파이프라인 · 텐서 나누기와 전송 몫 (BM7)
```

참고한 것은 기법의 이름과 공개 논문 · 형식 명세뿐이고 코드는 모두 새로 작성했습니다 — 층 단위 디스크 스트리밍(AirLLM 등), 전문가 CPU 오프로드 · 전문가 캐시(ktransformers · llama.cpp 의 MoE 오프로드), 페이지 어텐션 · 연속 배칭(vLLM 등), 삼진 가중치(BitNet b1.58 논문), GGUF(공개 형식 명세).

## 설계

- **머리말만 읽어 정확히 센다(BM1).** '파라미터 수 × 비트' 로 어림하면 틀립니다: 같은 Q4_K_M 이라도 텐서마다 형식이 다르고(임베딩 · 출력은 Q6_K 등), MoE 는 전문가 텐서가 대부분입니다. GGUF 는 머리말에 텐서마다 모양 · 형식 · 위치를 적어 두므로, 가중치를 읽지 않고 머리말만 읽어 텐서별 바이트를 계산합니다(형식표의 블록 크기 · 블록 바이트, 표에 없는 새 형식은 이웃 텐서의 위치 차). 가진 GGUF 6개에서 계산한 합이 파일 크기와 바이트 단위로 같았습니다. HF 모델은 config.json 만 받아 구조 × 비트로 어림하고, 어림이라는 사실을 표시합니다.
- **KV 는 층마다 센다(BM1).** '층 수 × KV 머리 × 차원 × 맥락' 은 요즘 모델에서 몇 배 틀립니다. 층마다 실제 K · V 차원(attn_k · attn_v 텐서 모양)을 보고, 슬라이딩 창 층은 창 길이까지만, 앞 층의 KV 를 나눠 쓰는 층(gemma-4 의 shared_kv_layers)은 0, 어텐션 대신 선형 어텐션 · 상태 공간을 쓰는 층(Qwen3.5 의 4개 중 3개 층)은 맥락과 상관없는 고정 상태로 셉니다.
- **토큰/초는 대역폭으로 어림한다(BM1).** 생성 한 토큰은 쓰는 가중치를 한 번 다 읽어야 해서 메모리 대역폭이 한계입니다(지붕선 모형). 장치마다 '그 장치에 둔, 이번 토큰에 쓰는 바이트 ÷ 대역폭' 을 더합니다. MoE 는 전문가 중 쓰는 몫(used/count)만 읽으므로, 전문가를 CPU 에 둬도 손해가 작습니다 — Qwen3-30B-A3B(Q4 어림 17GB, 전문가 16.2GB)는 GPU 8GB · RAM 대역폭 40GB/s 에서 '앞 37개 층 전문가만 CPU' 33.6 토큰/초 > '층 18개만 GPU' 28.9 > 전부 CPU 23.5 로 어림됩니다. 내장 GPU 는 GPU 메모리를 RAM 에서 나눠 쓰므로(선택) GPU 에 둔 만큼 RAM 에서 뺍니다. 어림은 계산 · 동기화 비용을 빼므로 실제보다 빠르게 나옵니다 — 그 차이를 BM3 실측으로 봅니다.
- **스트리밍은 같은 답부터(BM2).** 체크포인트를 텐서 하나씩 읽어 층마다 파일로 나눕니다(메모리보다 큰 모델도 나눌 수 있음). 모델은 설정으로 meta 장치에 만들어 가중치 메모리를 0 으로 두고, 층 밖 가중치(임베딩 · 정규화 · 출력)만 올립니다. 회전 위치 부호의 inv_freq 는 state_dict 에 없는 버퍼라 meta 에서는 값이 없어 그 모듈만 CPU 에 새로 만듭니다. 층 i 의 파일을 읽어 붙이고(assign) 계산한 뒤 meta 로 돌려 메모리를 놓습니다. KV 캐시는 층 번호로 쌓여 층을 갈아 끼워도 이어 읽기가 됩니다. 마스크는 모델 본체와 같은 함수로 만들어, 시험 모델에서 통째 실행과 로짓 최대 차이 0 · 생성 토큰 8/8 일치를 확인했습니다. 미리 읽기는 지금 층을 계산하는 동안 다음 층 파일을 다른 스레드에서 읽습니다. 생성 한 토큰마다 모든 층을 다시 읽으므로, 긴 글을 한 번 읽는 일(미리 채우기)이 토큰 하나를 만드는 일과 같은 비용입니다 — '읽기는 많고 생성은 적은' 일(채점 · 분류 · 요약의 미리 채우기)에 맞습니다.
- **배치는 실측으로 확인한다(BM3).** 계획의 배치 인자(-ngl N · --cpu-moe · --n-cpu-moe N)를 그대로 llama-server 에 넣어 차례로 띄우고, 같은 질문의 생성 · 미리 채우기 토큰/초(서버 timings) · 서버가 적은 KV 크기 · RSS 를 잽니다. 계획의 어림과 나란히 보여 어림을 믿을 수 있는지 봅니다. 전문가 쓰임은 라우터에 훅을 달아 토큰마다 고른 전문가를 기록하고(transformers 5 의 라우터 모듈은 Linear 가 아니라 (전문가 수, 은닉) 가중치를 가진 모듈이라 모양으로 찾음), 층마다 상위 10% 전문가의 몫과 'GPU 에 전문가 C 개만 둘 때 적중률' 을 정책별(미리 센 인기 전문가 고정 · LRU · LFU)로 셉니다. 흉내 기록에서 고르게 쓰이면(치우침 0) 10% 를 둬도 적중 9.5%, 치우침 1.2 면 10% 로 55% 였습니다 — 일부만 GPU 에 두는 전문가 캐시는 실제 모델의 쓰임이 치우쳐 있을 때만 의미가 있습니다.
- **KV 는 블록으로 나눠 쓴다(BM4).** 요청마다 최대 길이만큼 미리 잡으면 실제로는 메모리가 남는데도 새 요청을 받지 못합니다. 요청은 블록 번호 목록(블록 표)만 갖고, 가득 찬 블록은 '앞 블록 해시 + 이 블록 토큰' 으로 해시해 같은 내용이면 같은 물리 블록을 참조 수만 늘려 씁니다. 덜 찬 마지막 블록은 요청마다 따로 둡니다(이어 쓰면 내용이 달라짐 — 쓰기 시 복사 대신 '찬 블록만 공유' 로 단순하게). 같은 2GB · 같은 요청 120개에서 미리 잡기(4096)는 평균 동시 6.8 · 잡은 칸의 27% 만 찼고, 페이지는 21.0 · 99%, 앞부분 공유는 23.3 · 물리 칸당 1.55 토큰이었습니다(흉내). 다만 공유로 프롬프트를 싸게 받으면 한꺼번에 너무 많이 받아, 생성 중 새 블록이 모자라 기다리는 일이 생깁니다 — 요청 80개에서는 공유가 평균 동시 14.6 으로 페이지(17.4)보다 낮았습니다. 실제 서버는 이때 나중 요청을 빼서 다시 계산(선점)하므로, 받을 때 생성 몫의 블록을 남겨 두는 규칙이 필요합니다.
- **걸음마다 넣는다(BM5).** 고정 묶음은 가장 긴 요청이 끝날 때까지 나머지 자리가 놀고, 끝난 자리도 묶음이 끝날 때까지 계산합니다(채움). 걸음 시간 모형(기본 + 자리당 + 미리 채우기 토큰당)으로 같은 포아송 도착을 두 방식으로 돌려 처리량 · 대기 포함 지연 · 첫 토큰 · 자리 쓰임을 봅니다. 실제 서버는 슬롯 수(-np) × --cont-batching / --no-cont-batching 으로 띄워 같은 동시 부하로 잽니다(서버 시작 인자의 -np 1 은 뒤에 준 값이 덮음, 맥락은 슬롯마다 같게 슬롯 수만큼 곱함).
- **품질 절벽을 같은 글로 본다(BM6).** 작은 공개 LM 의 선형층을 학습 없이 64개 묶음 반올림 8 · 4 · 3 · 2비트와 삼진(묶음 평균 절댓값 눈금으로 −1 · 0 · +1)으로 줄여 같은 글의 혼란도 · 원래와 다음 토큰 1위 일치 · KL 을 봅니다. 반올림은 0 을 가운데 두지 않는 '칸 가운데 값'((i + ½)·눈금)을 씁니다 — 0 을 가운데 두면 2비트가 −1 · 0 · +1 세 단계만 써서 삼진과 같아졌습니다. 임베딩 · 출력층은 그대로 둡니다(이 모델은 둘을 같이 쓰고, 실제 GGUF 도 높은 비트로 둠). 학습 없이 2비트 · 삼진으로 줄이면 무너지는 것이 정상이고, 처음부터 저비트로 학습한 모델만 버틴다는 것을 같은 표로 보이려는 것입니다. 가진 GGUF 는 실제 가중치당 비트(파일 바이트 × 8 ÷ 파라미터)를 봅니다 — 이름보다 실제 비트가 높습니다: gemma-4-E4B Q4_0 은 5.51비트(바이트의 56% 가 Q6_K), UD-Q2_K_XL 은 3.98비트(54% 가 Q4_K), kanana-2-3B Q4_K_M 은 4.92비트.
- **전송이 이득을 먹는 지점을 계산한다(BM7).** 파이프라인은 층을 메모리 비율로 이어서 나누고, 토큰마다 기기들이 차례로 일하므로 한 요청을 빠르게 하지 않습니다(메모리만 늘어남, 경계마다 지연 + 은닉 벡터). 텐서는 층마다 행렬을 대역폭 비율로 나눠 동시에 읽지만 층마다 두 번 결과를 모아야 해서 (지연 × 2 × 층 수) 가 붙습니다. Qwen3-32B(Q4 어림 18GB)를 PC 20GB · 40GB/s + 노트북 12GB · 50GB/s 로 나누면, 1Gbit 이더넷 · 0.5ms 에서 파이프라인 2.4 · 텐서 3.7 토큰/초(전송 몫 26%), 10Gbit · 0.05ms 에서 텐서 4.9(전송 몫 3%)로 어림됩니다. 실측은 다른 기기에서 rpc-server 를 띄우고 그 주소를 BM3 의 배치 실측에 --rpc 로 넣어 같은 길로 잽니다.
