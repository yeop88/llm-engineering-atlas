# 리랭킹 — 방법 · 실측

1단계 검색(벡터 · BM25)이 고른 후보를 더 정밀한 모델로 다시 줄 세웁니다. 화면은 `/rerank`(리랭킹 테스트)입니다.

## 방법

| 방법 | 원리 | 비용 |
|---|---|---|
| 크로스 인코더 (리랭커 11종) | 질문과 후보를 한 번에 읽어 관련도 점수 — 쌍마다 독립 | 후보 수 × 쌍당 시간 (CPU 10개 약 22초) |
| LLM 목록형 | 번호 붙인 후보들을 한 번에 보여 주고 관련 순서를 JSON 으로 받음 | 질문당 LLM 1번 (후보는 짧게 잘라 문맥에 넣음) |
| 리랭크 융합 | 리랭커 순위와 1단계 순위를 RRF 로 합침 | 추가 비용 없음 |

설계에서 고른 것과 이유:

- **LLM 은 목록형으로.** 후보마다 부르는(pointwise) 방식은 후보 수만큼 호출해 로컬 LLM 으로는 너무 느립니다. LLM 이 일부 번호만 돌려주거나 형식을 어기면 돌려준 번호를 앞에, 나머지는 원래 순서로 둡니다(검색 결과를 잃지 않게).
- **융합.** 실측(연결 실행 #1)에서 리랭커가 1단계의 1위 정답을 끌어내려 Hit@1 이 80 → 50% 로 떨어진 적이 있습니다. 두 순위가 모두 높은 후보를 앞에 두면 한쪽의 실수를 다른 쪽이 메웁니다(점수 척도가 달라 순위로 합침).
- **평가는 한 번만 계산.** 크로스 인코더는 쌍마다 독립이라 가장 큰 후보 수에서 한 번 점수를 매기고, 작은 후보 수의 결과는 앞부분만 잘라 계산합니다. 지연은 '쌍당 시간 × 후보 수'로 환산합니다(모델 로드 시간은 따로).
- LLM 리랭커는 단계 의존 규칙(2 RAG 는 뒤 단계를 모름) 때문에 연결 계층(`run_search`)에서 끼워 넣습니다. 검색 설정에 `"llm_rerank": {"top": 10, "fusion": false}` 또는 `"rerank_fusion": true` 를 넣으면 검색 비교 · 평가 · 답변 · 연결 실행 어디서든 적용됩니다.

## 실측

### #1 · 2026-10-18 · 공공문서 · 직접 작성 24문항 (run #232)

- 1단계: KURE-v1 의미 검색(정확 검색). 리랭커: Qwen3-Reranker-0.6B(CPU, 로드 4.7초 별도), LLM 목록형: Gemma 4 E4B(QAT Q4_0), 후보 300자.
- 기준 대비 = '리랭킹 없음'과의 질문별 nDCG@10 짝지은 차이(%p)와 95% 구간.

읽은 것

- **1단계(KURE 의미 검색)가 이미 강해 리랭커 단독은 오히려 떨어졌습니다.** 후보를 많이 넣을수록 더 떨어졌습니다(5 → 20개: −3.7 → −6.1%p) — 후보가 많으면 리랭커가 틀린 것을 위로 올릴 기회도 늘기 때문입니다. 연결 실행 #1 에서 본 'Hit@1 하락'과 같은 현상입니다.
- **융합이 그 손실을 거의 없앴습니다**(−3.7 → +0.8). 두 순위가 모두 높은 후보를 앞에 두니 리랭커의 실수를 1단계가 메웠고, 구간도 좁아졌습니다(덜 들쭉날쭉). 리랭커를 쓴다면 융합과 함께 쓰는 것이 안전합니다.
- LLM 목록형 + 융합이 가장 높았지만(91.2) 차이는 불확실하고, 질문당 28초로 크로스 인코더 상위 5개(11초)보다 비쌉니다.
- 결론: 이 자료 · 이 1단계에서는 **리랭킹이 지연만 늘리고 이득은 확인되지 않았습니다.** 1단계가 약한 경우(BM25 · 작은 임베딩 모델 · 긴 문서)나 GPU 에서 다시 재야 합니다. 리랭킹은 라우팅으로 '어려운 질문'에만 쓰는 편이 맞습니다.
