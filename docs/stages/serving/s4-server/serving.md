# 서빙 · 추론 최적화 — 동시 부하 · KV 캐시 · 추측 디코딩 · 예산 · 자원 · 실측 (S1~S7)

화면은 `/serving/bench`(부하 · 디코딩 실측) · `/serving/budget`(비용 · 지연 예산 · 자원), 코드는 `app/stages/serving/` 입니다.

## 설계

- **동시 부하(S4).** 같은 질문 묶음을 동시 요청 수(1 · 2 · 4 …)의 두 배만큼 한꺼번에 보내 처리량(요청/초 · 출력 토큰/초)과 지연(p50 · p95)을 잽니다. 두 배를 보내는 이유는 줄서기까지 보려는 것 — llama-server 의 동시 슬롯(`-np`)보다 많이 오면 줄을 서서 p95 가 늘어나고, '몇 명까지 받을 수 있나'가 여기서 나옵니다. 프롬프트 캐시는 끕니다(앞 요청이 같은 프롬프트를 처리해 둔 덕을 보지 않게).
- **KV 캐시 · 추측 디코딩(S5)은 앱이 서버를 띄운다.** 사람이 명령을 바꿔 가며 서버를 다시 띄우면 설정 · 순서 · 데우기가 매번 달라 비교가 흔들립니다. 그래서 앱이 같은 모델 · 같은 문맥 길이로 설정만 바꿔 빈 포트(18100~)에 차례로 띄우고 끕니다(`launcher.py`). KV 의 V 를 양자화하려면 flash attention 이 필요해 함께 켭니다. 추측 디코딩은 같은 계열의 작은 초안 모델(`-md`)을 씁니다 — 어휘가 다르면 서버가 시작하지 못하고, 그 설정만 실패로 남습니다.
- **채점은 양자화 비교와 같은 곳에서.** 같은 질문 · 같은 근거(검색은 한 번)로 LLM 양자화 비교(7b, `llm_bits.evaluate`)를 그대로 돌립니다 — '빨라졌지만 나빠졌나'를 같은 기준으로 보려고. 첫 설정(보통 f16 · 추측 없음)이 기준이고, 질문별로 짝지어 품질 차이 · 유의성 · 생성 속도 배수를 냅니다.
- **메모리는 두 가지로.** 서버가 시작할 때 로그에 적는 KV 캐시 크기(비트를 바꾼 효과가 바로 보이는 정확한 값)와 프로세스 RSS(CPU 메모리 — Vulkan · CUDA 로 GPU 에 올린 가중치 · 캐시는 여기 안 잡힘). 초안 수락률도 로그에서 읽습니다.
- **예산(S7)은 이미 잰 것에서.** 후보를 새로 재지 않고 연결 비교(flow_eval) · LLM 양자화(quant_llm) · 라우팅 평가(routing_eval)의 결과를 모읍니다. 같은 평가 세트끼리만 품질을 비교할 수 있어 세트별로 묶고, 목표(p95 지연 · 질문당 비용 · 최저 품질) 안에서 품질이 가장 좋은 것과 파레토 앞줄을 보입니다. 목표 안이 없으면 가장 가까운 것과 무엇을 넘었는지. 운영 쪽은 요청 기록으로 경로 · 모델별 p95 · 질문당 비용 · 목표를 넘은 비율을 봅니다.
- **자원 현황(S1 · S2 · S3 · S6).** 캐시 적중(AS 의미 캐시 · 검색 향상 변형 캐시) · 올라간 임베딩 · 리랭커(장치 · dtype) · 장치 빌드 · 메모리 · LLM 경로(기본 · 소형 · 대체)를 한 화면에 — 무엇이 지금 메모리를 쓰고 있는지 모르면 모델을 더 올리거나 캐시를 늘리는 결정을 할 수 없습니다.
