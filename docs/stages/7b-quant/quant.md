# 양자화 — 방법 · 실측

숫자를 낮은 정밀도로 줄여 메모리 · 속도를 얻고, 그 대가로 정확도가 얼마나 떨어지는지 잽니다. 화면은 `/quant`(양자화 테스트)입니다. **임베딩 벡터**와 **LLM 가중치**를 따로 비교합니다.

## 여러 양자화를 동시에 (조합)

- **임베딩**: 고른 모델 가중치 × 차원 × 벡터 정밀도의 모든 조합을 같은 질문으로 채점합니다. 예) `모델 int8 동적 + 256차원 + binary 재점수` = 인코딩은 빨라지고 벡터는 32바이트. 인코딩은 가중치 변형마다 한 번만 하고 차원 · 정밀도는 그 임베딩을 잘라 · 바꿔 가며 점수만 다시 매깁니다. 기준(float32 가중치 · 전체 차원 · float32)과 질문별로 짝지어 비교하고, 메모리 대비 정확도에서 다른 조합에 지지 않는 **파레토 최적** 조합을 표시합니다.
- **LLM**: 가중치 양자화(GGUF 파일)와 KV 캐시 양자화를 함께 적용한 `llama-server` 실행 명령을 화면에서 만들고(`LLM_MODELS_DIR` 의 파일 목록), 띄운 서버들을 같은 근거로 비교합니다. 앱이 서버를 직접 띄우지는 않습니다 — 메모리를 크게 쓰는 외부 프로세스라 언제 띄우고 끌지는 사용자가 정하게 했습니다.

## 임베딩 벡터 양자화

| 정밀도 | 저장 | 벡터당 메모리 (1024차원) | 검색 |
|---|---|---|---|
| float32 (기준) | 실수 그대로 | 4,096 B | 내적 |
| int8 | 차원마다 문서 임베딩의 최소~최대를 256칸으로 나눔 | 1,024 B (1/4) | 정수 내적 |
| binary | 0보다 크면 1 | 128 B (1/32) | 해밍 거리 |
| binary + int8 재점수 | binary 는 메모리, int8 은 디스크 | 128 B (+ 디스크 1,024 B) | 해밍으로 후보 k × 배수 → float32 질의 · int8 문서로 다시 점수 |

설계에서 고른 것과 이유:

- **공개 검색 벤치마크로 잰다**(Ko-StrategyQA 300문항 등). 양자화 손실은 보통 1~2%p 라 질문이 적은 내 평가 세트로는 우연과 구분되지 않습니다.
- **같은 float32 임베딩을 한 번만 만들고 정밀도만 바꿉니다.** 차이가 오직 저장 정밀도에서 오도록.
- 정확도는 두 가지로 봅니다: 정답 기준 nDCG@10(float32 와 질문별 짝지은 비교)과, 정답과 무관한 **float32 상위 10개 유지율**(양자화 오차 자체).
- int8 범위는 **문서 임베딩으로 보정**합니다 — 서비스에서도 색인할 문서로 보정하므로.
- binary + 재점수는 RAM 에는 binary 만 두고 후보의 int8 만 디스크에서 읽는 구성(벡터 DB 들이 쓰는 방식)을 흉내 냅니다.
- 검색 시간은 numpy 로 전수 비교한 값이라 실제 벡터 DB 속도와 다릅니다 — 정밀도끼리의 상대 비교용입니다.

## LLM 양자화 (GGUF 비트 수)

같은 모델(Gemma 4 E4B)의 GGUF 를 비트 수만 바꿔 같은 질문 · **같은 근거**로 답하게 합니다. 검색은 질문마다 한 번만 하고 모든 모델에 같은 근거를 주므로 모델 차이만 남습니다. 품질은 정답 근거를 인용했는가(없으면 문장 근거율), 첫 번째 모델(가장 정밀한 것)과 질문별로 짝지어 비교합니다.

- llama-server 는 서버 하나에 모델 하나라, 모델마다 다른 포트에 띄우고 `.env` 의 `OPENAI_MODEL_URLS` 에 이름 → 주소를 적습니다. 이 설정은 6 라우팅의 빠른 경로에 작은 모델을 붙일 때도 그대로 씁니다.

```powershell
llama-server.exe -m gemma-4-E4B-it-Q8_0.gguf       --port 8082 -c 8192 -ngl 99 -np 1 --alias gemma-4-e4b-q8
llama-server.exe -m gemma-4-E4B-it-UD-Q2_K_XL.gguf --port 8083 -c 8192 -ngl 99 -np 1 --alias gemma-4-e4b-q2
# .env
OPENAI_MODEL_URLS={"gemma-4-e4b-q8": "http://127.0.0.1:8082/v1", "gemma-4-e4b-q2": "http://127.0.0.1:8083/v1"}
```

## 실측

### LLM #1 · 2026-10-18 · 같은 근거로 GGUF 비트 수 비교 (run #230)

- 모델: Gemma 4 E4B. Q8_0(ggml-org, 8.0GB) · **QAT Q4_0**(Google, 5.2GB, 지금 기본) · UD-Q2_K_XL(unsloth, 3.8GB). llama.cpp b11669 Vulkan, 내장 GPU(AMD Radeon, 공유 메모리), 서버마다 `-c 8192` (기본 서버만 `-c 16384 -np 2`).
- 자료: 공공문서 · 직접 작성 24문항, KURE-v1 의미 검색 근거 5개(질문당 약 2,000토큰)를 세 모델에 똑같이 줌. **프롬프트 캐시를 끄고** 측정.

읽은 것

- **QAT Q4_0 이 Q8_0 과 같은 품질로 가장 빨랐습니다.** 학습 단계에서 4비트 오차에 맞춘 QAT 판이라 4비트 손실이 드러나지 않았고, 메모리 대역폭이 병목인 내장 GPU 에서 가중치가 작을수록 생성이 빨라졌습니다(6.9 → 13.0 tok/s).
- **2비트는 더 작지만 더 빠르지 않았습니다.** 생성 속도는 Q4 와 같고, 읽기(프롬프트 처리)는 오히려 느렸습니다 — 2 · 3비트 K 양자화는 계산할 때 복원 비용이 커 연산이 병목인 읽기 단계에서 손해를 봅니다. 답변이 길어지고(102 토큰) 근거 인용은 8%p 떨어졌습니다(24문항이라 불확실).
- **RAG 에서는 '읽기'가 시간의 대부분입니다(질문당 25~31초 중).** 근거를 5개 · 2,000토큰 넣기 때문입니다. 생성 속도보다 근거 길이 · 수(문맥 압축, 근거 수 줄이기)와 프롬프트 캐시가 체감 속도를 더 좌우합니다.
- 측정 실수와 정정: 첫 측정(run #229)에서는 Q4 만 질문당 6초로 나왔는데, 앞선 라우팅 평가가 같은 질문 · 같은 근거를 이미 처리해 llama-server 의 **프롬프트 캐시**가 재사용된 탓이었습니다(로그상 읽은 토큰 5개). 비교 측정 요청에 `cache_prompt: false` 를 보내도록 고치고, 서버가 주는 단계별 시간으로 읽기 · 생성 속도를 나눠 기록하게 한 뒤 다시 쟀습니다(run #230).
- 결론: 이 PC 의 기본 LLM 은 지금처럼 QAT Q4_0 이 맞습니다. 6 라우팅의 빠른 경로에 더 작은 모델을 붙이려면 같은 모델의 저비트보다 **작은 모델(7a 증류)** 을 찾아야 합니다.
