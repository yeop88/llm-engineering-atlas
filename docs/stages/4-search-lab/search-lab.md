# 검색 향상 — 기법 · 측정 기록

임베딩 모델과 인덱스는 그대로 두고, **검색 전에 질의를 LLM 으로 다듬어** 검색 품질을 올리는 단계입니다. 화면은 `/search-lab`(검색 향상 테스트)이고, 같은 기능을 2 RAG 의 검색 비교 · 조합 평가 · 답변 생성에서도 검색 설정의 `enhance` 로 켤 수 있습니다.

## 기법

| 기법 | 하는 일 | 잘 맞는 경우 | 위험 |
|---|---|---|---|
| 질의 재작성 (`rewrite`) | 구어체 · 상황 설명형 질문을 문서 용어가 든 검색어 한 줄로 바꿈 | "빨래 기계 물이 안 빠져요" → "세탁기 배수 필터 청소" 처럼 문서와 낱말이 어긋난 질문, 특히 BM25 | 원 질의에만 있던 조건(날짜 · 고유명사)을 빼먹음 |
| HyDE (`hyde`) | LLM 이 질문에 답하는 *가상 문서 단락*을 쓰고, 그 단락을 **문서 역할로 인코딩**해 검색 | 질문은 짧은데 정답 문서는 긴 설명문일 때(질문-문서보다 문서-문서 유사도가 안정적) | LLM 이 사실과 다른 내용을 쓰면 엉뚱한 문서로 끌려감, 생성이 길어 가장 느림 |
| 다중 질의 (`multi`) | 관점 · 용어가 다른 질의 `n`개로 각각 검색 | 질문이 모호하거나 여러 문서에 걸칠 때 | 검색 횟수가 `n+1` 배, 관계없는 변형이 노이즈를 섞음 |

## 어떻게 동작하나

```
질문 ─┬─ (원 질의) ───────────────┐
      └─ LLM 변형 1..n ─ 각각 같은 검색(의미 · BM25 · 하이브리드) ─┴─ RRF 합치기 ─ (리랭커: 원 질의로 한 번) ─ 상위 k
```

설계에서 고른 것과 이유:

- **검색 엔진을 고치지 않고 감쌌다.** 변형을 만든 뒤 기존 검색(`rag.service.search`)을 여러 번 부르고 합칩니다. 어떤 검색 방식과도 조합되고, 기법을 끄면 결과가 이전과 정확히 같아 기준선이 흔들리지 않습니다.
- **원 질의 결과도 합친다(기본).** 재작성 · HyDE 는 원 질의가 이미 잘 맞는 질문을 망칠 수 있어, 원 질의 결과와 RRF 로 합쳐 손해를 줄입니다. `keep_original: false` 로 변형만의 효과를 따로 잴 수 있습니다.
- **점수가 아니라 순위로 합친다(RRF).** 원 질의와 HyDE 단락의 코사인 점수는 분포가 달라 점수 합은 한쪽으로 쏠립니다.
- **HyDE 단락은 문서 역할로 인코딩한다.** E5 · EmbeddingGemma 처럼 질의/문서 프롬프트가 다른 모델에서 가상 문서를 질의 프롬프트로 인코딩하면 '문서-문서 유사도'라는 HyDE 의 전제가 깨집니다.
- **리랭커는 합친 뒤 원 질의로 한 번만.** 리랭커는 비싸고(CPU 질문당 수십 초), 최종 판단은 LLM 이 바꾼 문장이 아니라 사용자가 실제로 물은 것에 맞춰야 합니다.
- **LLM 변형은 temperature 0 + 질문별 캐시.** 조합 평가는 같은 질문을 설정마다 다시 검색하므로, 캐시하면 LLM 호출이 '질문 수'로 줄고 설정끼리 같은 변형으로 비교됩니다(LLM 무작위성이 설정 간 차이에 섞이지 않음). 캐시는 프로세스 메모리라 서버를 다시 켜면 비워집니다.
- **LLM 실패는 검색 실패로 드러낸다.** 빈 변형으로 조용히 원 질의만 검색하면 "기법 효과 없음"으로 잘못 기록되기 때문입니다.
- **연결점 하나로 모든 화면에 적용.** 검색 API 들은 `app/pipeline/search.py` 의 `run_search` 를 거칩니다. 단, 파인튜닝 전후 비교는 '모델'만 비교해야 하므로 검색 향상을 거치지 않습니다.

결론

- **이 세트에서는 어떤 기법도 유의하게 좋아지지 않았고, 질의 재작성은 BM25 에서 유의하게 나빠졌습니다.** 의미 검색 기준선이 이미 Hit@10 100% · nDCG 89.9 로 천장에 가까워 올라갈 여지가 작았습니다.
- 재작성이 나빠진 이유(질문별로 확인): 작은 LLM 이 질문을 짧은 명사구로 **압축하면서 결정적인 낱말을 빼거나 바꿨습니다.** 예) "공문서에서 오후 3시 20분은 어떻게 표기하나요?" → "공문서 시간 표기법"(1위 → 4위), "'문의 바람' 같은 명령조 문장은…" → "명령조 문장 교정 방법"(1위 → 7위), "성별과 나이를…" → "성별 및 연령 기재 적절성"(1위 → 10위 밖, 문서에는 '나이'라고 씀). BM25 는 낱말 일치에 기대므로 이 손실이 그대로 드러났습니다.
- 다중 질의는 하이브리드에서 +3.8%p(Hit@1 62.5 → 70.8)로 가장 나아 보였지만 구간이 넓어 확정할 수 없고, 비용은 질문당 LLM 약 6.5초입니다.
- 이 평가 세트는 직접 쓴 사실 확인형 질문이 많아 문서와 낱말이 이미 많이 겹칩니다. 기법의 효과가 크다고 알려진 **구어체 · 상황 설명형 질문**이 많은 세트(예: 고객 · AS 문의)로 다시 재야 합니다.
- 다음에 해 볼 것: 재작성 프롬프트에 "고유명사 · 숫자 · 따옴표 안 표현은 그대로 둘 것"을 넣고 다시 측정, 질문 유형(상황 설명형)에만 기법을 켜는 적응형 적용.

## 해석할 때 주의

- 지연에는 LLM 변형 생성 시간이 들어갑니다. 같은 평가를 다시 돌리면 캐시 때문에 LLM 시간이 0 이 되므로, 지연은 **첫 실행** 값을 봅니다.
- 질문이 적으면 몇 %p 차이도 우연일 수 있습니다. 결과 표의 '차이 불확실'은 1위와의 짝지은 비교에서 95% 구간이 0 을 포함한다는 뜻입니다.
- 평가 세트가 '문장 추출'형이면 질문이 문서 문장 그대로라 향상 기법이 거의 도움이 되지 않습니다(이미 낱말이 일치). 구어체 · 상황 설명형 질문이 든 세트로 재야 합니다.
