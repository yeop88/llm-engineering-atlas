# 파싱 점검 · OCR · 표 · 그림 (D2 · D3)

화면은 `/docintel/parsing`(컬렉션 파싱 보고 · 문서별 쪽 글 · OCR · 표 · 그림 추출)입니다.

## D2 파싱 점검 · OCR

- 문서마다 쪽별 글자 수 · 빈 쪽 · 깨진 글자 비율(대체 문자 · 제어 문자 · 자모만 이어진 조각)을 보고 문제 문서만 걸러 봅니다.
- **스캔 PDF 도 받습니다.** 예전에는 글이 없는 PDF 를 업로드에서 거절했는데, 그러면 OCR 로 채울 문서 자체가 없습니다. 이제 빈 쪽으로 받아 'OCR 필요'로 표시하고, OCR 로 글이 생기면 표시를 지웁니다.
- OCR: 원본 PDF 쪽을 그림으로 그려(pypdfium2, 2배 = 144dpi) 비전 LLM 에게 글로 옮기게 합니다. 로컬은 llama-server 에 `--mmproj`(비전 프로젝터)를 붙인 Gemma 4 E4B.
- **글이 이미 있는 쪽은 덮어쓰지 않고 정확도만 잽니다.** 파서가 뽑은 글이 OCR 보다 정확하므로 바꾸면 손해이고, 이 수치로 빈 쪽 OCR 결과를 얼마나 믿을지 정합니다.

## D3 표 · 그림

- pdfplumber 로 쪽마다 표를 찾아 마크다운 표로 바꾸고 쪽 글에 `[표 p-n]` 블록으로 넣습니다. 표가 글 줄로 흩어지면 '어느 코드가 어느 조치인지'가 끊겨 검색 · 인용이 틀어지기 때문입니다.
- 그림 영역은 잘라 미디어 청크(1장 = 1청크)로 넣어 멀티모달 검색 · 답변 첨부에 씁니다.
- 원본에서 다시 뽑을 때 OCR 로 채운 쪽은 그대로 둡니다(원본 PDF 에는 그 쪽 글이 없어 지워지던 버그를 고침).

## 실측 (2026-10-21, 정답이 있는 PDF)

공개 PDF 는 원본 보관 전에 올려 다시 처리할 수 없어서, 정답을 아는 PDF 를 만들었습니다: A4 3쪽(머리말 '고객지원 운영 지침 (사내 한정)', 꼬리말 쪽 번호, 본문 문장, 표 2개 — 오류 코드 6×4 · 처리 기한 4×3). 글 층이 있는 판과, 같은 쪽을 그림으로만 넣은 스캔판을 같이 올렸습니다.

| 측정 | 결과 |
|---|---|
| 표 추출(글 판, pdfplumber) | 표 2/2, 모양 일치, 셀 **36/36** 글자까지 같음 |
| 스캔판 OCR — 본문 문장 재현율 | **99.4%** (179자 중 놓친 것: '세탁기' → '세탁') |
| 스캔판 OCR — 표 셀 재현율 | **100%** (115자, 표를 `|` 로 나눈 글로 옮김) |
| 글 판 OCR 정확도(파서 글과 비교) | 92.7% (쪽별 1.0 · 0.874 · 0.906) |
| OCR 시간 | 쪽당 약 26초 (gemma-4-e4b Q4, Vulkan) |
| 머리말 · 꼬리말 찾기 | 두 판 모두 머리말 줄 · 쪽 번호 패턴을 찾음 |

- 글 판 정확도가 스캔판 재현율보다 낮은 것은 비교 대상 차이입니다 — 파서 글은 표를 칸마다 줄을 바꿔 뽑고 OCR 은 표를 `|` 로 이은 한 줄로 옮겨, 글자 정렬이 어긋납니다. 본문 문장만 보면 스캔판처럼 거의 일치합니다.
- 한계: 만든 PDF 는 글꼴이 깨끗하고(맑은 고딕) 기울기 · 얼룩이 없습니다. 실제 스캔본(기울어진 쪽 · 도장 · 손글씨)에서는 낮아집니다. 표도 선이 다 그려진 표라 pdfplumber 에 쉬운 경우입니다.
