# 지식 그래프 · GraphRAG — 구축 · Cypher · 그래프 확장 · 실측 (K1~K8)

화면은 `/kg/build`(그래프 구축) · `/kg/explore`(그래프 탐색 · Cypher) · `/kg/rag`(GraphRAG), 코드는 `app/stages/kg/` 와 그래프 저장소 `app/core/graphstore.py` 입니다. 첫 도메인은 이미 있는 법률 공개 자료(법령 6 · 대법원 판례 164)입니다.

```
K1 역량 질문 ─ K2 온톨로지 ─ K3 추출(정형 + LLM 쟁점) ─ K4 합치기 ─ K5 내장 그래프 저장소(원본) ─ Neo4j · FalkorDB 로 옮기기 ─ K6 Text2Cypher
                                                                      ├─ K7 검색 결과 → 그래프 이웃 확장 → GraphRAG 답변
                                                                      └─ K8 커뮤니티 탐지 → 묶음 요약 → 전체 질문
```

## 설계

- **원본은 앱 DB, Cypher 는 Neo4j.** 그래프 DB 서버 없이도 그래프를 만들고 이웃 확장 · 커뮤니티를 돌릴 수 있어야 실험이 막히지 않습니다(벡터 저장소가 Qdrant 로컬 파일 모드로 서버 없이 도는 것과 같은 이유). 노드 · 관계 표(마이그레이션 0012)가 원본이고, Text2Cypher 는 실제 Cypher 엔진이 있어야 의미가 있어 Neo4j(docker compose `neo4j` 프로필, 5.26 LTS)로 통째로 옮깁니다. 두 곳에 따로 쓰면 어긋나므로 쓰기는 늘 앱 DB 에만 합니다. Neo4j 에는 그래프 하나만 둡니다 — LLM 이 만든 쿼리에 그래프 조건이 빠져도 섞이지 않게.
- **Cypher 엔진 둘(Neo4j · FalkorDB).** 같은 그래프를 두 엔진에 옮겨 같은 역량 질문으로 비교합니다 — Neo4j 는 JVM 기반이라 무겁고, FalkorDB 는 Redis 모듈(희소 행렬로 그래프를 표현)이라 가볍지만 Cypher 방언이 다릅니다(OpenCypher + 자체 확장, 예: `EXISTS { }` 하위 쿼리가 없음). 쓰기 차단도 엔진마다 다릅니다: Neo4j 는 `EXPLAIN` 쿼리 종류, FalkorDB 는 읽기 전용 명령 `GRAPH.RO_QUERY` 가 서버에서 쓰기를 거절합니다. 엔진은 요청마다 고르고(`engine`), 고르지 않으면 `GRAPH_ENGINE`. 결과 모양(노드는 이름)은 두 엔진이 같게 맞춰 채점이 엔진과 상관없게 합니다. ArangoDB(AQL, 다중 모델)는 Cypher 가 아니어서 Text2Cypher · 역량 질문을 따로 만들어야 해 보류했습니다.
- **K1 역량 질문 15개**(`app/stages/kg/presets/legal_cq.json`): 한 단계 조회 · 여러 단계 · 집계 · 없는 것 찾기. 벡터 RAG 는 집계 · 없는 것 찾기에 답하지 못합니다 — 문서 몇 개를 읽어서는 '모든 판례 중 몇 개'를 셀 수 없어서. 질문마다 기대 Cypher 를 두어 Text2Cypher 의 정답으로 씁니다.
- **K2 온톨로지**(`legal_ontology.json`): 클래스 5(법령 · 조문 · 판례 · 쟁점 · 커뮤니티) · 관계 6(속함 · 참조 · 인용 · 판례 인용 · 다룸 · 구성원). 역량 질문이 묻는 것만 둡니다 — 개념이 늘수록 관계 이름이 흩어져 쿼리할 수 없는 그래프가 됩니다. 추출 결과 검증 · Text2Cypher 스키마 설명 · 화면이 모두 이 파일에서 나옵니다.
- **K3 정형 먼저.** 법령의 조문 머리(`제23조(해고 등의 제한)`), 시행령의 `법 제N조`, `「법령」 제N조`, 판례의 【참조조문】 · 【참조판례】는 형식이 정해져 있어 LLM 없이 정확히 뽑힙니다. 판례가 다루는 쟁점처럼 형식이 없는 것만 LLM 으로 판시사항에서 1~3개 뽑습니다(형식이 어긋나면 그 판례는 쟁점 없이 — 지어낸 쟁점보다 낫다). 자료에 본문이 없는 인용 대상(민법 조문 · 다른 판례)도 '바깥' 노드로 둡니다 — '민법 제750조를 인용한 판례' 같은 질문에 답하려면 필요합니다.
- **참조조문 전용 파서.** 처음에는 답변 인용 검사용 정규식(`app/stages/rag/legal.py`)을 썼는데, 법령 이름 안의 띄어쓰기를 허용하지 않아 '여객자동차 운수사업법' → '운수사업법', '상가건물 임대차보호법' → '임대차보호법', '노동조합 및 노동관계조정법' → '노동관계조정법' 처럼 잘렸습니다(상가건물 임대차보호법 조문이 주택임대차보호법과 비슷한 이름의 엉뚱한 노드로 묶임). 참조조문 칸은 형식이 정해져 있어 따로 읽습니다: 개정 연혁 괄호를 지우고, 쉼표 · 빗금으로만 나누고('및' · 가운뎃점은 법령 이름 안에도 있음), 법령 이름이 없는 조각은 앞 조각의 법령을 이어 씁니다. 이것으로 판례 → 조문 인용이 317개에서 694개로 늘었습니다.
- **K4 합치기.** 법령 · 조문 이름은 규칙으로 정규화합니다(띄어쓰기 · 가운뎃점 '·'/'ㆍ' · '구' 법 · 조문 번호 표기). 쟁점은 낱말 끝 조사 · 띄어쓰기를 뺀 글자가 같으면 합치고, 그 밖에는 임베딩 유사도 0.88 이상끼리 합칩니다(합친 기록을 화면에). 기준을 낮추면 다른 쟁점이 하나로 뭉쳐 '같은 쟁점 판례' 확장이 엉뚱한 판례를 끌고 옵니다.
- **K6 Text2Cypher**: 스키마 설명은 온톨로지에서 자동으로, 예시 2개, 읽기 쿼리만. 쓰기 쿼리는 실행 전에 Neo4j 의 `EXPLAIN` 으로 쿼리 종류를 보고 읽기('r')가 아니면 막습니다(FalkorDB 는 `GRAPH.RO_QUERY`) — 읽기 접근 모드는 단일 서버에서 쓰기를 막지 못하고, 키워드 검사는 우회가 쉽습니다. 실행 오류 · 빈 결과면 이유를 알려 다시 쓰게 합니다(최대 2번, 빈 결과가 답일 수도 있어 빈 결과 재시도는 한 번).
- **K7 그래프 하이브리드**: 검색 상위 5개 결과의 문서를 그래프 노드로 바꿔(판례 문서 → 판례 노드, 법령 청크 → 청크 앞 조문 머리의 조문 노드) 2단계 이웃을 봅니다 — 인용한 조문 · 판례, 같은 조문을 인용한 다른 판례(공동 인용), 같은 쟁점. 넓힌 문서는 '연결 수'(직접 연결 2점 · 공유 이웃 1점)로 줄 세워 **벡터 결과 뒤에** 붙입니다 — 벡터 1위를 밀어내지 않게. 답변에는 문서 사이 관계를 '관계 요약'으로 시스템 프롬프트에 넣고(내용의 근거로는 쓰지 말라는 규칙과 함께), 검증 · 가드레일 · 요청 기록은 다른 답변과 같습니다.
- **K8 커뮤니티**: 조문 · 판례 · 쟁점 그래프에서 Louvain 커뮤니티를 찾습니다. 법령 노드와 '속함'은 뺍니다 — 넣으면 법령마다 한 덩어리가 돼 '같은 문제를 다루는 조문 · 판례' 묶음이 아니라 법령 목차가 됩니다. 큰 묶음부터 LLM 요약을 만들어 커뮤니티 노드로 저장하고, 전체 질문은 질문과 가까운 요약 4개로 한 번에 답하며 [C1] 처럼 묶음을 인용합니다.

### K6 Cypher 엔진 비교 — Neo4j 5.26 vs FalkorDB 4.22

같은 그래프(커뮤니티 포함 노드 1,414 · 관계 3,027)를 두 엔진에 옮기고, 역량 질문 15개의 기대 Cypher 를 API 로 5번씩 실행했습니다.

| | Neo4j 5.26.32 community | FalkorDB v4.22.0 |
|---|---|---|
| 옮기기 | 1.3초 | 0.7초 |
| 기대 Cypher 15개 실행 · 결과 일치 | 15/15 | 15/15 (두 엔진 결과가 모두 같음) |
| 쿼리 지연(API 포함, 질문별 중앙값의 중앙값) | 14.6ms | 5.1ms |
| 첫 실행 지연(계획 · 캐시 데우기 전) | 37.6ms | 5.7ms |
| 컨테이너 메모리(적재 후) | 810~828MiB (힙 상한 1G) | 73~77MiB |
| 쓰기 쿼리 차단 | `EXPLAIN` 쿼리 종류 → 403 | `GRAPH.RO_QUERY` → 403 |

Text2Cypher(LLM 이 쓴 Cypher, 같은 15문항, 정확 일치):

| 엔진 · 단계 | 정확 일치 | 같은 답(다른 속성) | 오류로 끝남 | 비고 |
|---|---|---|---|---|
| Neo4j (#334) | 66.7% | 73.3% | 0 | |
| FalkorDB (#335) | 66.7% | 66.7% | 2 | 한글 별칭 `AS 판례명`, `EXISTS { }` 하위 쿼리가 문법 오류 |
| 프롬프트에 공통 문법(영문 별칭 · 패턴 조건) — Neo4j (#336) · FalkorDB (#337) | 60.0% · 60.0% | 66.7% · 66.7% | 0 · 1 | 별칭 오류는 사라짐, 모델이 `EXISTS { }` 는 세 번 모두 다시 씀 |
| + FalkorDB 실행 전 `EXISTS { (패턴) }` → 패턴 조건 변환 — Neo4j (#340) · FalkorDB (#341) | 60.0% · 66.7% | 66.7% · 73.3% | 0 · 0 | |

해석:

- **엔진은 정확도를 가르지 않습니다.** 기대 Cypher 는 두 엔진이 같은 답을 내고, LLM 이 쓴 쿼리의 차이는 방언 두 가지(따옴표 없는 한글 별칭 · `EXISTS { }`)뿐이었습니다. 프롬프트 규칙 + 변환(`app/core/graphstore.py` `falkor_dialect`) 뒤 FalkorDB 오류는 0 입니다. 남은 오답은 두 엔진에서 같은 질문(여러 단계 cq-7 · cq-9 · cq-13, 이름을 돌려준 cq-10)이라 LLM 의 한계입니다.
- 한 실행 안의 60% ↔ 66.7% 차이는 1문항이고, 같은 프롬프트 · 온도 0 에서도 질문별 출력이 실행마다 달라(llama.cpp 병렬 슬롯) 엔진 차이로 읽으면 안 됩니다.
- **FalkorDB 가 가볍고 빠릅니다** — 메모리 약 1/11, 지연 약 1/3, 첫 실행에서 데우기 비용이 거의 없음. 이 규모(노드 1.4천)에서는 둘 다 사람이 느끼지 못하는 지연이라, 고르는 기준은 무게 · 운영 도구(Neo4j 콘솔 · 생태계) · 방언입니다. 기본 엔진은 Neo4j 그대로 두고 `GRAPH_ENGINE` 로 바꿉니다.

### K1 역량 질문 — 1차 → 2차 (Neo4j)

| | 1차 (#325) | 2차 (#332) |
|---|---|---|
| 정확 일치 | 40% | 53% |
| 한 단계 조회 · 집계 · 여러 단계 · 없는 것 찾기 | 100 · 33 · 0 · 50% | 100 · 50 · 0 · 100% |

1차의 '없는 것 찾기' 실패 원인은 데이터였습니다: 바깥(자료에 본문이 없는) 노드에만 `external: true` 를 달고 자료 안 노드에는 속성을 두지 않아, `external = false` 조건이 늘 비었습니다. 모든 노드에 `external` 을 달았습니다(`app/stages/kg/extract.py`). 또 정답이 사건번호인데 판례 이름으로 답한 경우를 '같은 답(다른 속성)'으로 따로 셉니다 — 정확 일치만 보면 Text2Cypher 가 실제보다 나빠 보입니다.

### K7 그래프 하이브리드 검색 (LLM 없이, 평가 세트)

벡터 상위 k 와 '벡터 + 그래프로 넓힌 문서'의 정답 문서 hit(하나라도) · all(모두):

| 평가 세트 · k | 벡터 hit · all | + 그래프 hit · all | 넓혀서 새로 찾은 정답 |
|---|---|---|---|
| #5 7유형 218문항 · k=10 (2차 #328) | 98.2 · 97.7 | 97.2 · 96.8 | 1 |
| #5 · 여러 문서 9문항 · k=10 | 100 · 88.9 | 88.9 · 77.8 | 0 |
| #5 · k=5 (#329) | 93.6 · 93.1 | 88.5 · 87.2 | 5 |
| #7 142문항 · k=10 (#330) | 97.9 · 97.9 | 99.3 · 99.3 | 2 |
| #7 · k=5 (#331) | 96.5 · 96.5 | 95.1 · 95.1 | 4 |

**이 자료에서 그래프 확장은 검색을 낫게 하지 않습니다.** 1차(#323 · #324)와 같은 결론이고, 2차에서 k=5 로 줄여(벡터가 놓친 정답이 더 많은 조건) 다시 봤습니다. 넓혀서 새로 찾은 정답(4~5개)보다, 넓힌 문서가 벡터 결과의 자리를 차지해 빠진 정답이 더 많았습니다. 여러 문서 질문(9문항)도 나빠졌습니다 — 이 평가 세트의 여러 문서 질문은 '같은 주제의 두 판례'라 인용 관계로 이어져 있지 않습니다. 그래프 확장은 '조문 → 그 조문을 인용한 판례'처럼 관계 자체를 묻는 질문에 맞고, 그런 질문은 Text2Cypher 가 더 정확히 답합니다(한 단계 조회 100%). 확장은 지연 35~72ms 입니다.

### K8 커뮤니티 · 전체 질문
