# 토크나이저 · 표현 공간 — 글 종류별 토큰 효율 · 표시 쪼개짐 · 어휘 · 정규화 · 임베딩 · 위치 · 이미지 토큰 · 실측 (TK1~TK6)

화면은 `/tokenizer/compare`(토크나이저 비교), 코드는 `app/stages/tokenizer/` 입니다. 모델마다 토크나이저 파일 · config.json 만 받습니다(가중치 없음). 임베딩 공간의 성질(비등방성 · 언어 간 정렬)은 해석 맵(IP1)에서 잽니다.

```
같은 글 5종(일반 한국어 · 법령 · AS 매뉴얼 · 코드 · 영어) × 모델 → 1,000자당 토큰 · 가장 적은 모델 대비 (TK2)
표시 8개(WM-200 · E4 · d80 · 제3조의2 · 제43조 · 날짜 · 전화번호 · 30분) → 토큰 수 · 조각 · 바이트 조각 여부 (TK2)
어휘 크기 · 한글 조각 몫 · 한 글자 조각 · 특수 토큰 (TK3) / 정규화 형태별 토큰 (TK1)
config → 임베딩 · 출력층 크기(같이 쓰나) (TK4) · 회전 위치 θ · 확장 · 최대 (TK5) · 이미지 한 장 토큰 (TK6)
```

## 설계

- **토큰 수가 비용 단위.** 같은 '맥락 32K' 도 한국어 글자당 토큰이 1.5배인 모델에는 실제로 넣을 수 있는 글이 2/3 입니다. 미리 채우기 시간(IF2) · KV · 요금 모두 토큰에 비례하므로, 같은 글 종류를 모델마다 나눠 1,000자당 토큰과 가장 적은 모델 대비 배율을 봅니다. 시험 모델로 확인한 Qwen3 은 한국어 글(일반 · 법령 · 매뉴얼) 1,000자에 716~773 토큰, 코드 · 영어는 약 240 토큰이었습니다 — 같은 글자 수의 한국어가 맥락을 3배 넘게 씁니다.
- **표시가 쪼개지는 모양.** 압축의 보호 규칙(KC1) · 검색의 코드 규칙이 기대는 표시가 몇 토큰으로 어떻게 나뉘는지 봅니다. 바이트 조각(토큰 하나를 풀면 깨진 글자)이 생기는 토크나이저는 토큰 경계와 글자 경계가 달라, 토큰 단위로 지우거나 자르는 처리에서 글자를 깨뜨립니다 — 압축 맵에서 실제로 이 문제로 정답률이 무너졌습니다(KC1 문서).
- **정규화는 토큰 수로 확인(TK1).** NFC · NFD(자모 분리) · 전각 숫자 · 보이지 않는 문자(폭 없는 공백) 형태의 같은 글을 나눠 토큰 수를 비교합니다. 토크나이저가 스스로 정규화하면 같고, 아니면 늘어납니다 — 늘어나면 캐시가 맞지 않고 검색 · 보호 규칙이 빗나가므로 정제(D4)에서 맞춰야 합니다. Qwen3 은 NFD · 전각 숫자를 같은 토큰으로 바꿨고, 보이지 않는 문자는 토큰을 19% 늘렸습니다.
- **어휘는 효율과 메모리를 맞바꾼다(TK3 · TK4).** 어휘가 크면 글자당 토큰이 줄지만 임베딩 · 출력층(어휘 × 은닉)이 커집니다. 작은 모델일수록 출력층이 토큰당 읽는 양의 큰 몫이라(TA6) 이 맞바꿈이 중요하고, 출력층과 임베딩을 같이 쓰는지(tied)도 함께 봅니다.
- **위치 · 이미지도 토큰으로(TK5 · TK6).** 회전 위치 θ · 확장 방식 · 최대 위치는 긴 맥락 실측(CX2)과 함께 읽고, 이미지 한 장의 토큰(패치 수 ÷ 병합², 또는 설정의 이미지당 토큰)은 사진 질문이 맥락 예산을 얼마나 쓰는지 정합니다.

해석:

- **같은 한국어 글의 토큰 수가 모델마다 2.3배까지 다릅니다.** 일반 한국어 1,000자가 A.X 에서는 305 토큰, Qwen3 에서는 716 토큰입니다. 같은 '32K 맥락'에 넣을 수 있는 한국어 글이 2배 넘게 차이 나고, 미리 채우기 시간 · KV · 요금도 그만큼 곱해집니다. 이 앱의 작은 LM(Qwen3-0.6B)은 한국어 토큰 효율이 가장 낮습니다. 압축(KC1) · 해석(IP) 실측의 토큰 수가 큰 이유입니다.
- **영어 · 코드는 모델 사이 차이가 작습니다(239~310).** 차이는 한국어 어휘에서 나옵니다. 한글 조각 몫이 큰 모델(A.X 59% · EXAONE 33% · kanana 24%)이 한국어에서 적은 토큰을 씁니다. 다만 kanana 는 몫(24%)보다 효율이 좋아서(법령 · 매뉴얼 1위), 몫만으로 효율을 예측할 수는 없습니다.
- **자모 분리(NFD) 글은 한국어 어휘가 큰 모델에서 3~6배로 불어납니다.** macOS 에서 온 파일 이름 · 일부 웹 글이 NFD 입니다. Qwen 계열 · A.X 는 토크나이저가 스스로 NFC 로 맞춰 영향이 없고, kanana · EXAONE · HyperCLOVAX 는 그대로 자모 단위로 나눕니다. 문서 정제(D4)에서 NFC 로 맞추는 것이 필수입니다. 보이지 않는 문자(폭 없는 공백)는 모든 모델에서 토큰을 19~45% 늘립니다.
- **숫자 · 코드 표시는 kanana · HyperCLOVAX 가 짧게 나눕니다.** 전화번호 7 토큰 vs 13 토큰입니다. 숫자를 여러 자리씩 묶는 토크나이저이기 때문입니다. 압축 보호 규칙(KC1)이 지켜야 하는 토큰도 그만큼 적습니다.
- **출력층을 따로 두는 모델은 A.X 뿐입니다.** 어휘 102,400 × 은닉 3,584 의 출력층(367M)이 임베딩과 별도라, 토큰마다 읽는 양에 그만큼 더해집니다(구조 맵 TA6).

한계: 글 종류마다 한두 문장이라 1,000자당 값은 거칩니다. 실제 문서 묶음의 토큰 수로 다시 재는 것이 정확합니다.
