# 이미지 · Vision-Language — 입력 확인 · 전처리 · 영역 찾기 · 영역만 읽기 · 꺾임 규칙 · 매뉴얼 근거 답 · 근거 영역, VLM 하나에 vs 나눠서 (VL1~VL7)

화면은 `/vision/look`(사진 읽기 · 근거 영역), 코드는 `app/stages/vision/` 입니다. 표시창 읽기와 코드 맞춤은 사진 진단(AS4)의 것을 씁니다.

```
사진 → 형식 · 크기 · 회전 표시 · 위치 정보(EXIF GPS) 지우기 (VL1)
  → 표시창 찾기(어두운 네모 덩어리) → 주축으로 기울기 되돌리기 → 다시 찾기 (VL2 · VL3)
  → 표시창만 잘라 키움 → 반사 누르기 · 선명하게(그 영역만) → 비전 LLM 이 읽음 → 알려진 코드에 맞춤 (VL4)
  → 호스(가늘고 긴 회색 덩어리) 중심선의 방향 변화 → 꺾임 (VL5, 규칙)
  → 읽은 것을 질문에 붙여 서비스 답변(매뉴얼 근거) (VL6) → 답 문장마다 기댄 영역 번호 · 영역 그림 (VL7)
비교: 사진 전체 + 질문을 비전 LLM 한 번에(코드 · 꺾임 JSON) vs 위의 나눠서
```

## 설계

- **VLM 하나에 다 맡기지 않습니다.** 사진 하나를 비전 LLM 에 주고 '코드는? 호스는 꺾였나?'를 물으면, 틀렸을 때 표시창을 못 찾았는지, 찾았는데 못 읽었는지, 꺾임을 잘못 봤는지 알 수 없습니다. 그래서 일을 나눕니다.
  - 영역 찾기와 꺾임은 규칙으로 합니다. 빠르고, 근거 값(채움 · 방향 변화)이 남습니다.
  - 글자 읽기만 비전 LLM 에 맡기고, 잘라 키운 표시창만 보여 줍니다.
  - 각 단계의 결과가 따로 남아, 어디서 틀렸는지 압니다.
- **시험 사진을 '실제 고객 사진처럼' 어렵게 만들었습니다.** 사진 진단(AS4)의 시험 그림은 표시창이 가운데에 크게 있었습니다. 실제 고객 사진은 다릅니다.
  - 멀리서 찍어 앞판이 작고(0.45~0.6배), 잡동사니와 표시창처럼 어두운 띠가 함께 찍힙니다.
  - 기울고(±12도), 흐리고, 표시창에 빛이 반사됩니다.
  - 배수 호스(곧음 · 꺾임)를 더했습니다.
  - 정답(코드 · 표시창 영역 · 호스 영역 · 꺾임 · 기울기)을 알아서 각 단계를 따로 채점합니다.
- **표시창은 '사진마다 정한 어둠'으로 찾습니다(VL3).** 처음에는 밝기 55 미만을 어둡다고 봤습니다. 그러자 반사가 표시창 가운데를 밝혀 덩어리가 쪼개졌고, 기울기 · 반사 · 흐림 사진 24장에서 표시창을 하나도 찾지 못했습니다. 이렇게 고쳤습니다.
  - 기준을 '가장 어두운 3% + 45'(55~110)로 정합니다.
  - 덩어리를 닫고 구멍(밝은 글자 · 반사)을 메웁니다.
  - 채움 · 가로세로 비를 축에 맞춘 상자가 아니라 주축으로 돌린 상자로 잽니다. 기운 표시창은 축 상자로 재면 채움이 0.5 아래로 떨어집니다.
- **읽기용 보정과 모양 규칙은 다른 그림을 씁니다(VL2).** 처음에는 반사 누르기 · 선명하게를 사진 전체에 쓰고 그 그림에서 호스도 찾았습니다. 언샤프가 테두리에 밝고 어두운 띠를 만들고 감마가 회색 값을 옮겨서, 깨끗한 사진의 호스 꺾임 정답률이 100% → 40% 로 떨어졌습니다. 지금은 기울기만 사진 전체를 되돌리고, 반사 누르기 · 선명하게는 잘라 낸 표시창에만 씁니다.
- **영역만 잘라 키워 읽힙니다(VL4).** 표시창 + 여백 15% 를 잘라 짧은 변 320px 까지 키우고 대비를 높입니다. 멀리서 찍은 사진의 작은 글자를 비전 LLM 이 읽을 크기로 보여 주려는 것입니다. 표시창을 못 찾으면 사진 전체를 읽히고, 그 사실('사진 전체에서')을 남깁니다.
- **꺾임은 규칙으로 봅니다(VL5).** 호스 중심선(가로 위치마다 세로 중앙값)을 12토막으로 나눠, 이웃 토막의 방향이 한 번에 50도 넘게 바뀌면 꺾임으로 봅니다. 최대 방향 변화를 근거로 남깁니다.
- **사진을 LLM 에 두 번 주지 않습니다(VL6).** 답할 때는 사진에서 읽은 것('표시창 오류 코드 d80, 배수 호스가 꺾여 있음')을 질문에 붙여, 평소의 서비스 답변(입력 방어 → 검색 → 근거 검증)으로 매뉴얼 근거 답을 받습니다. 사진은 읽기 단계에서 한 번만 씁니다.
- **답 문장마다 기댄 영역을 붙입니다(VL7).** 문장이 코드를 말하면 표시창 영역, 호스 · 배수 · 꺾임을 말하면 호스 영역 번호를 붙입니다. 영역이 없는 문장은 매뉴얼 근거에만 기댄 것으로 표시합니다. 영역 상자를 그린 그림을 같이 돌려줍니다.
- **위치 정보는 지웁니다(VL1).** 휴대폰 사진의 EXIF 에는 GPS(고객 집 위치)가 들어 있을 수 있습니다. 회전 표시를 실제 회전으로 바꾼 뒤 EXIF 를 버리고, 지웠다는 사실만 남깁니다.

## 실측

2026-10-23. 영역 찾기 · 꺾임 규칙은 맞출 때 쓴 씨앗(0~23)과 겹치지 않는 씨앗 100~129 로, 조건마다 30장을 재었습니다(LLM 없음).

| 조건 | 표시창 찾음 | 표시창 IoU | 기울기 오차(도) | 호스 꺾임 정답 |
| --- | --- | --- | --- | --- |
| 깨끗 | 100% | 0.987 | 0.0 | 100% |
| 멀리서 | 100% | 0.977 | 0.0 | 96.7% |
| 기울기 · 반사 · 흐림 | 93.3% | 0.914 | 0.22 | 100% |
| 멀리서 + 기울기 · 반사 · 흐림 | 100% | 0.968 | 0.13 | 93.3% |

해석:

- 규칙 부분은 어려운 사진에서도 표시창을 93~100% 찾고, 기울기를 0.2도 안쪽으로 잽니다. 놓친 표시창(2장)은 반사가 표시창의 절반 넘게 덮은 사진이었습니다. 이때는 사진 전체를 읽히는 안전망으로 넘어갑니다.
- 호스 꺾임은 멀리서 찍어 호스가 짧고 가늘어질 때(폭 4~9px) 틀립니다. 토막당 화소가 적어 방향이 흔들리기 때문입니다.

'VLM 하나에' vs '나눠서'의 코드 · 꺾임 정답률(비전 LLM gemma-4-E4B)은 실측 중인 다른 LLM 실험이 끝난 뒤 덧붙입니다.

한계:

- 표시창 · 호스 규칙은 이 앱의 시험 사진(가전 앞판 그림)에 맞춘 것입니다. 실제 사진에서는 이 자리(`see.find_display` · `find_hose`)를 작은 탐지 모델로 바꿔야 합니다. 나눠서 하는 구조와 단계별 채점은 그대로 씁니다.
- 꺾임 외의 관계(위 · 옆 · 연결)는 아직 없습니다.
