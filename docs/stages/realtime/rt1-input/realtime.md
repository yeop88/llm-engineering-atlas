# 실시간 스트리밍 — 지터 · 손실 · 끊김을 섞은 스트림 재생, 단계별 꼬리 지연 · 확정 오류 · 끼어들기 · 세션 복구 (RT1~RT8)

화면은 `/realtime/stream`(스트림 재생 · 꼬리 지연), 코드는 `app/stages/realtime/` 입니다. 재생기(`sim.py`)는 계산만 하므로 바로 답합니다. 실제 LLM 의 첫 토큰 실측(`live.py`)은 작업으로 돌립니다.

```
발화(낱말마다 330ms) → 조각(chunk_ms) → 망: 기본 지연 + 지터(오른쪽 꼬리가 긴 로그 정규), 손실이면 재전송(왕복 + 편도) 또는 포기 (RT1)
  → 지터 버퍼(buffer_ms) → 순서대로 → 조각마다 인식(고정 + 소리 길이 비례) (RT2)
  → 가설 → 연속 일치 확정(agree, OM2) · 확정 오류 · 깜빡임 (RT3) → 확정마다 대화 상태(제품 · 코드, C3) (RT4)
  → 문장 끝이 확정되면 검색 미리 시작 (RT5)
  → 끝점(말 끝 + 마지막 조각 지연 + endpoint_ms) → 검색 → 첫 토큰 → 첫 문장 → 첫 합성 → 망 편도 = 첫 소리 (RT6)
끼어들기 → 소리 멈춤: 서버 취소 vs 기기에서 멈춤 (RT7) · 말하는 도중 끊김 → 복구 전략별 잃은 말 (RT8)
발화 6개 × 씨앗 N → p50 · p95 · p99
```

## 설계

- **평균이 아니라 꼬리로 봅니다.** 실시간 대화는 평균이 1초여도 열 번에 한 번 3초 걸리면 어색합니다. 그래서 한 설정을 발화 6개 × 씨앗 50개(300턴)로 다시 틀어 p50 · p95 · p99 를 봅니다. 망 지터는 정규 분포가 아니라 로그 정규로 둡니다. 정규 분포로 두면 '대부분 작고 가끔 크게 튀는' 지연을 못 만들어 p99 를 낮게 잡습니다.
- **있는 부품을 엮습니다.**
  - 부분 인식 확정은 옴니채널의 연속 일치 규칙(OM2 `Stabilizer`)과 인식기 흉내(`simulate`, 잠정 꼬리가 비슷한 소리로 틀렸다가 고쳐짐)를 씁니다.
  - 상태는 대화 메모리 갱신(C3)을 씁니다.
  - 답 쪽 지시문은 음성 짧은 지연 RAG(VC3)의 것을 씁니다.
  - 새로 만든 것은 망 · 버퍼 · 시간 흐름과 끼어들기 · 복구 모형뿐입니다.
- **끝점은 망 지연만큼 늦습니다.** 서버는 '말이 끝났다'를 말 끝 뒤 침묵 조각이 도착해야 압니다. 그래서 끝점 = 말 끝 + 마지막 조각의 지연 + 침묵 확인(500ms)입니다. 이동 중 LTE 에서 끝점 대기의 p95 가 1초를 넘는 이유입니다.
- **상태는 끝점 확정 뒤에 채점합니다.** 처음에는 마지막 확정(끝점에서 남은 잠정까지 확정) 전에 상태를 채점했습니다. 그러면 확정이 늦은 설정일수록 상태가 덜 찬 채로 채점되어, 확정 오류가 0인 agree=3 의 상태 정확이 88% 로 나왔습니다. 고친 뒤에는 100% 입니다.
- **끼어들기는 어디서 멈추느냐로 봅니다(RT7).** 서버가 끼어들기를 감지해 취소를 보내면, 고객 기기는 이미 받은 소리를 계속 틉니다. 그래서 멈춤 지연 = 감지(200ms + 조각 길이 안의 대기) + 망 왕복 + 기기 재생 버퍼입니다. 기기가 스스로 재생을 멈추면 감지 시간만 남습니다.
- **복구는 상태를 어디 두느냐로 봅니다(RT8).** 말하는 도중 1초 끊겼다 다시 붙는 경우를 세 전략으로 봅니다.
  - 새 세션: 서버가 받은 것도 이어 쓰지 못합니다.
  - 서버 보관: 서버가 확정분을 들고 있습니다. 끊긴 동안 말한 것과 망에 떠 있던 것은 잃습니다.
  - 서버 보관 + 다시 보냄: 기기가 확인(ACK)을 못 받은 소리를, 끊긴 동안 녹음한 것까지 다시 보냅니다.
  - 다시 보낼 때 조각 순번이 없으면, 서버가 이미 받았지만 확인이 기기에 못 간 낱말이 겹칩니다. 그 수도 셉니다.
- **가짜로 만든 것을 밝힙니다.** 망 · 인식기 · 합성 시간은 분포로 흉내 낸 것이고, 씨앗이 같으면 같은 결과가 나옵니다. LLM 시간만은 실제 스트리밍으로 재어(RT6 실측) 바꿔 넣을 수 있습니다.

해석:

- **1.2초 예산은 끝점 대기 때문에 지켜지지 않습니다.** LLM 이 빨라져도(GPU 가정) 첫 소리 p50 이 1.5초입니다. 가장 큰 단일 몫은 끝점 대기(p50 633ms)입니다. 음성 맵의 예산(VC3)은 끝점에 34%(408ms)를 주지만, 침묵 확인 500ms 에 망 지연이 더해져 그 몫을 혼자 넘깁니다. 줄일 곳은 LLM 이 아니라 끝점입니다. 글을 보고 끝을 앞당기는 의미 끝점(VC2), 끝점 전에 답을 미리 만들어 두는 추측 생성이 그 방법입니다.
- **이 PC 에서는 첫 문장이 병목입니다.** 12.5 토큰/초로 14토큰 첫 문장에 1.1초가 걸립니다. 같은 끝점에서도 첫 소리 p50 이 2.8초라, 실시간 음성은 이 PC 의 내장 GPU 로는 무리입니다.
- **검색 미리 시작의 이득은 작습니다(평균 50ms).** 확정된 글이 끝점 전에 문장 끝('…요', '…다')에 닿는 턴이 40% 남짓입니다. 닿아도 줄일 수 있는 것은 검색 몫(120ms)뿐입니다. 이 장치는 검색이 비쌀 때(재순위 · 큰 인덱스) 의미가 커집니다.
- **확정 일치 수는 2보다 3이 낫습니다.** agree=1 은 잠정 꼬리의 오인식을 그대로 확정해, 제품 · 코드 상태가 세 번에 한 번 틀립니다(64%). agree=3 은 확정 오류 0, 상태 100% 이고 첫 소리 p95 는 3ms 늘 뿐입니다. 끝점에서 어차피 다 확정하므로 늦은 확정의 비용이 거의 없습니다. 실시간 음성(OM2)의 기본 agree=2 를 3으로 올릴 근거입니다. 다만 인식기 흉내의 오류율(잠정 꼬리 40%)이 실제 인식기와 같은지는 확인하지 않았습니다.
- **긴 조각이 확정 오류를 줄입니다.** 500ms 조각에서는 가설이 한 번에 1~2낱말씩 늘어, 흔들리는 마지막 낱말이 확정 일치에 걸릴 기회가 줄어듭니다(확정 오류 0.30 → 0.07). 이동 중 LTE 에서는 조각 수가 적어 손실 · 지터를 덜 맞으므로 p95 도 오히려 낮아집니다(2,142 → 2,001). 조각을 짧게 쪼개는 것이 늘 빠른 것은 아닙니다.
- **재전송을 끄면 지연 이득은 거의 없고 말을 잃습니다.** 손실 2% 에서 재전송을 끄면 p95 가 2,142 → 2,150 으로 그대로이고, 턴당 0.18~0.25 낱말을 못 듣습니다. 재전송이 늦어지는 조각은 대부분 끝점 대기 안에 묻히기 때문입니다.
- **지터 버퍼는 인식 경로에 이득이 없습니다.** 인식은 조각을 순서대로 처리하므로, 버퍼는 지연(버퍼 길이만큼)만 더합니다. 버퍼가 필요한 곳은 고객이 듣는 재생 쪽(끊김 없이 들리게)입니다.
- **끼어들기는 기기에서 멈춰야 합니다.** 서버가 취소를 보내면 망 왕복과 재생 버퍼만큼 소리가 더 나갑니다. 이동 중 LTE 에서 p95 1.1초 동안 고객의 말과 답이 겹칩니다. 기기가 스스로 멈추면 437ms 입니다.
- **세션 복구는 '서버 보관 + 다시 보냄'만 잃지 않습니다.** 서버가 확정분을 들고 있어도, 끊긴 동안 말한 것과 망에 떠 있던 것 때문에 39~42% 를 잃습니다. 기기가 확인받지 못한 소리를 들고 있다 다시 보내야 100% 이어집니다. 이때 조각 순번이 없으면 턴당 0.3~0.6 낱말이 겹치므로 순번으로 걸러야 합니다.

한계:

- 망 · 인식기 · 합성은 분포 흉내라 실제 서비스의 수치가 아닙니다. 결론은 '어느 단계가 꼬리를 만드는가'와 '설정 사이의 차이'로 읽어야 합니다.
- 인식기 흉내는 낱말 단위로 가설을 늘리고, 실제 인식기의 지연 · 오류 패턴(문맥으로 앞을 고침)을 다 담지 못합니다.
- 끊김은 1초 한 번만 봤습니다.
