# 추론 최적화 — 워크로드 · 미리 채우기 · 생성 분리 · 최적화 사다리 · 품질 게이트 · 실측 (IF1~IF9)

화면은 `/inference/workload`(워크로드 측정) · `/inference/ladder`(최적화 사다리), 코드는 `app/stages/inference/` 입니다. 기법 자체는 서빙(S4 · S5) · 큰 모델(BM1 · BM3~BM5) · 압축(KC5) · 양자화(7b) 맵에 있고, 이 맵은 그것들을 **기준선 → 메모리 압력 완화 → 배칭 · 캐시 → 추측 디코딩 → 품질 확인 → 카나리** 순서로 한 표에 묶습니다.

```
요청 기록 → 프롬프트 · 답 토큰 · 단계 시간 · 동시 수 분포 (IF1)
탐침(길이를 바꾼 요청) → 미리 채우기 · 생성 토큰/초 → 워크로드에 곱해 시간 몫 · 병목 (IF2)
사다리: 기준선(f16 KV · 슬롯 1 · 요청 캐시 끔)
  → KV q8_0 / q4_0 (IF4) → 슬롯 2 / 4 · 연속 배칭 (IF5) → 앞부분 캐시 (IF6) → 추측 디코딩 (IF7) → 다른 비트 GGUF (IF3)
  칸마다: 같은 질문 · 근거의 품질 + 동시 부하의 p50 · p95 · 처리량 · 성공 작업당 장치 시간 → 앞 통과 칸과 짝지은 품질 차이로 게이트 (IF9)
병렬화(IF8)는 기기가 하나라 큰 모델 맵의 혼합 · 여러 기기 계획으로
```

## 설계

- **기준선부터(IF1).** 같은 기법도 프롬프트가 긴 워크로드(RAG)와 답이 긴 워크로드에서 효과가 반대입니다. 운영 요청 기록에서 프롬프트 · 답 토큰, 전체 · 단계별 시간의 p50 · p95 · p99 를 냅니다. 동시 수는 기록이 끝난 시각과 총 시간으로 요청 구간을 되살려 시작 · 끝 사건을 시각순으로 훑어 셉니다(최대 겹침 · 바쁠 때 평균) — 사다리의 동시 부하를 이 값으로 정합니다.
- **미리 채우기와 생성을 나눈다(IF2).** 요청 기록의 LLM 단계 시간은 둘이 섞인 값입니다. 프롬프트 · 답 길이를 바꾼 탐침 요청(캐시 끔 — 매번 처음부터 읽게)을 보내 서버가 알려 주는 단계 시간으로 미리 채우기 · 생성 토큰/초를 따로 재고, 워크로드의 p50 · p95 요청 길이에 곱해 시간 몫을 계산합니다. 몫이 큰 쪽이 먼저 줄일 곳입니다 — 미리 채우기면 앞부분 캐시 · 근거 줄이기 · 압축, 생성이면 양자화 · 추측 디코딩 · 답 길이 상한.
- **한 칸씩, 통과한 것 위에(IF3~IF7).** 칸은 llama-server 설정 하나(KV 비트 · 슬롯 수 + 연속 배칭 · 요청 캐시 · 초안 모델 · 다른 GGUF)입니다. 칸마다 서버를 띄워 같은 질문 · 같은 근거로 품질을 먼저 재고(부하가 서버 캐시를 데워 품질 측정 시간이 흐려지지 않게), 이어 동시 수의 두 배를 한꺼번에 보내 줄서기까지 봅니다. 통과한 칸만 다음 칸의 바탕이 되고(누적) — 실제 배포 순서와 같아서 — 같은 묶음(KV · 배칭)에서 하나가 통과하면 나머지는 건너뜁니다.
- **앞부분 캐시는 요청의 성질이다(IF6).** 서버 인자가 아니라 요청이 앞서 읽은 프롬프트를 다시 쓰게 하는 것(cache_prompt)이라, 기준선은 요청 캐시를 끄고 이 칸에서 켭니다. 부하 질문은 근거 두 묶음을 여러 질문이 나눠 쓰게 만들어 실제 RAG 처럼 같은 근거가 반복되게 했습니다.
- **평균보다 p95 · 성공 작업당 비용 · 품질 통과율(IF9).** 통과 조건: 바로 앞 통과 칸과 질문마다 짝지은 품질 차이의 신뢰 구간 하한이 −허용 하락(기본 0.02)보다 크고, p95 가 3% 이상 줄었거나 처리량이 3% 이상 늘었을 때. 비용은 GPU 요금표 대신 성공 요청 하나에 든 벽시계 장치 초(부하 시간 ÷ 성공 요청)로 셉니다. 끝에 남긴 칸의 기준선 대비 p95 · 처리량 · 장치 시간 배율과 카나리 순서(10% → 50% → 100%)를 보여 줍니다.
- **양자화 형식은 정답이 없다.** 같은 q8_0 KV 도 모델 · 장치 커널 · 맥락 · 동시 수에 따라 이득이 다릅니다. 그래서 사다리는 '좋다고 알려진 설정'을 적용하지 않고, 이 PC · 이 워크로드에서 다시 잽니다.

2026-10-23, gemma-4-E4B q4_0(llama-server, 내장 GPU).

**워크로드 (IF1, run #384)** — 운영 요청 기록 499건(토큰이 남은 404건)

| | p50 | p95 | p99 | 최대 |
| --- | --- | --- | --- | --- |
| 입력 토큰 | 837 | 2,555 | 2,767 | 2,997 |
| 출력 토큰 | 33 | 237 | 352 | 400 |

- 입력이 출력의 25배(평균 1,144 vs 64)인 RAG 워크로드입니다.

**미리 채우기 · 생성 나누기 (IF2)** — 서버가 이 판에서 단계별 시간을 돌려주지 않아(`split.available=false`) 탐침 6개의 전체 시간 차로 셈

| 입력 · 출력 토큰 | 초 |
| --- | --- |
| 256 · 64 / 256 · 256 | 6.3 / 20.7 |
| 1,024 · 64 / 1,024 · 256 | 13.7 / 28.8 |
| 2,048 · 64 / 2,048 · 256 | 33.0 / 47.8 |

- 출력 192토큰 늘리기 = +14~15초 → 생성 약 13 토큰/초. 입력 1,024 → 2,048 = +19초 → 미리 채우기 약 50~100 토큰/초(길수록 느려짐).
- 워크로드 p50(입력 837 · 출력 33)에 곱하면 시간의 약 80% 가 미리 채우기, p95(2,555 · 237)에서도 약 65% 입니다. **먼저 줄일 곳은 입력(앞부분 캐시 · 근거 줄이기 · 압축)** 입니다.

**최적화 사다리 (IF3~IF9, run #389)** — 질문 6개(품질) · 동시 2 로 4요청(부하), 칸마다 통과한 것 위에 누적

| 칸 | 품질 | p50 · p95 지연 | 처리량 토큰/초 | 성공당 장치 초 | 판정 |
| --- | --- | --- | --- | --- | --- |
| 기준선(f16 KV · 슬롯 1 · 캐시 끔) | 83.3% | 47.2 · 47.4초 | 3.1 | 23.7 | — |
| KV q8_0 | 83.3% | 49.1 · 56.8초 | 3.0 | 24.3 | 탈락(이득 3% 미만) |

- 남긴 칸(슬롯 2 + 앞부분 캐시)은 기준선보다 처리량 1.26배 · 성공당 장치 시간 0.80배이고, 품질은 그대로입니다.
- **p95 는 오히려 나빠졌습니다(47 → 64초).** 슬롯 2 로 두 요청을 같이 처리하면 하나하나는 느려지고, 4요청뿐이라 p95 가 가장 느린 한 요청입니다. 통과 조건이 'p95 또는 처리량 3%'라 처리량으로 통과했습니다. 상담처럼 한 사람의 지연이 중요하면 p95 를 필수 조건으로 바꿔야 합니다(할 일).
- KV q8_0 은 이 맥락 · 동시 수에서 이득이 없어 떨어졌습니다. 서빙 맵(S5)에서 메모리는 0.4 GB 줄었지만 속도는 같았고, 사다리는 메모리를 조건에 넣지 않습니다.
