# MA3 · 오케스트레이터 에이전트 (Orchestrator agent)

**상태: ⬜ 예정** — 복잡한 요청을 작업으로 쪼개(Task Decomposition) 전문가 에이전트에게 나눠 주고 결과를 모은다 — 라우터 자리의 진화

## 원리

오케스트레이터는 '작년 분기별 매출 그래프를 분석해 보고서를 쓰고 요약해 줘' 같은 요청을 검색 → 분석 → 작성 → 검증 작업으로 나누고, 작업마다 맞는 전문가 에이전트를 부르며, 중간 결과를 다음 작업에 넘깁니다. LLM 맵의 라우터가 '어느 경로로 보낼까'만 정했다면, 오케스트레이터는 '어떤 순서로 누구에게 무엇을' 정합니다.

## 왜 하는가

하나의 모델이 검색 · 계산 · 글쓰기 · 검증을 다 하면 프롬프트가 길고 실패 지점이 섞여 어디서 틀렸는지 알 수 없습니다. 역할을 나누면 에이전트마다 작은 모델 · 도구 · 검증을 따로 고를 수 있습니다. 다만 이 PC 의 실측에서 작은 로컬 모델은 여러 단계를 거친 답에서 근거 밖 문장이 늘었습니다(에이전트 문장 근거율 50% vs RAG 91%) — 단계를 늘릴수록 단계마다 검증이 필요합니다.

## 어떻게 (이 앱에서)

- (있음) LLM 맵 6 라우팅(규칙 · 확신도 · LLM · 학습 라우터)과 8a 에이전트(ReAct · 도구)가 출발점
- (예정) 작업 계획을 JSON(작업 · 담당 에이전트 · 입력 · 의존)으로 받아 실행 · 기록, 단순한 질문은 지금처럼 RAG 한 번으로(계획 비용을 아끼게)
- (예정) 평가: 같은 질문을 단일 에이전트 · 멀티에이전트로 풀어 품질 · 시간 · 호출 수 비교
