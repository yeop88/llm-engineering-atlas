# RLVR — 검증 가능한 과제 · 환경 · 보상 · GRPO · 보상 해킹 · 일반화 · 실측 (RV1~RV6)

화면은 `/rlvr/tasks`(과제 · 환경 · 보상) · `/rlvr/train`(GRPO 학습 · 보상 해킹) · `/rlvr/eval`(일반화 · 안전성), 코드는 `app/stages/rlvr/` 입니다. 학습한 정책은 후학습과 같은 표(`AppModel kind=llm_adapter, method=grpo`)에 두어 후학습 끝점(`pt-<번호>`)으로 불립니다.

```
법령 문서 · 지식 그래프 ─ 과제(조문 제목 · 번호 · 인용 수 · 계산) ─ 학습 / 시험(계산은 시험 전용)
   ↓ 환경: 도구 결과 기록 → 재생 (환경-실제 차이 점검)
   ↓ 정책(작은 LLM + LoRA): 과제마다 답 G개 → 검증 보상(정답 · 형식 · 길이 · 여러 답) → 묶음 상대 이점 → 학습(+ KL)
   ↓ 감시: 보상 ↑ 정답률 그대로 · 길이 · 여러 답 · 외움
   └ 평가: 학습 / 시험 · 유형별 정답률 + 레드팀(같은 공격)
```

## 설계

- **정답을 자동으로 확인할 수 있는 과제만.** 보상을 사람이 매기면 학습에 필요한 수천 번의 채점을 할 수 없고, LLM 판정은 그 자체가 틀립니다(검증 보정 실측). 그래서 자료에서 정답이 정해지는 과제를 만듭니다: 조문 제목 · 번호(법령 문서의 조문 머리 정형 추출), 판례 인용 수(지식 그래프의 인용 관계 집계), 그 두 수의 합(계산). 정답 확인은 정규화한 값으로 — 조문 번호는 '제23조' 모양, 수는 숫자, 제목은 띄어쓰기 · 문장부호를 뺀 글자 — 그리고 마지막 '정답:' 줄만 봅니다(본문 중간 숫자를 정답으로 잘못 읽지 않게).
- **시험에만 있는 유형.** 계산 유형은 학습에 넣지 않습니다. 학습한 유형만 잘하는지, 배운 능력(조회 + 집계)이 새 유형으로 옮겨 가는지를 보려는 것입니다(RV6).
- **기록 → 재생 환경.** 학습은 같은 과제를 수십 번 다시 풀므로 매번 실제 검색 · 집계를 부르면 느리고, 색인 · 그래프가 그사이 바뀌면 같은 과제의 보상이 달라져 학습 신호가 흔들립니다. 처음 한 번 기록하고 재생하되, 표본 과제를 다시 실제로 불러 겹침을 재 기록이 낡았는지 봅니다.
- **보상은 항목별로.** 정답(1) + 형식(0.1) − 길이(300자를 넘으면 조금씩) − 여러 답(정답 줄에 후보를 늘어놓으면 0.3). 항목별 기여를 남겨 '왜 이 보상인가'를 설명할 수 있게 합니다(8b 보상 함수와 같은 원칙).
- **GRPO.** PPO 는 가치 모델을 따로 학습해야 해 메모리 · 시간이 두 배인데, 정답 확인이 있는 과제는 같은 문제의 여러 답끼리 비교하면 기준선이 저절로 생깁니다(묶음 평균). 손실 = −(정규화한 이점 × 답 로그확률) + beta × KL(기준 = 어댑터를 끈 같은 모델, 메모리에 모델 둘을 올리지 않게). 묶음 보상이 모두 같으면(다 맞음 · 다 틀림) 배울 것이 없어 건너뜁니다 — 너무 쉽거나 어려운 과제를 거르는 효과도 있습니다.
- **보상 해킹 감시.** 정답 확인이 있어도 생깁니다: 보상은 오르는데 정답률은 그대로(보상이 형식 · 길이에서만 옴), 길이 부풀리기, 여러 답 늘어놓기(정답 확인이 첫 후보만 보게 막았지만 늘어나는지 감시), 학습 과제 정답률만 오르고 시험은 그대로(외움).
- **안전성.** 같은 공격 문항으로 레드팀을 함께 돌립니다 — 조회 · 계산을 잘하게 된 정책이 지시를 더 잘 따르게 되어 인젝션에 약해질 수도 있습니다.
