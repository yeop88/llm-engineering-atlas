# 옴니채널 · 실시간 멀티모달 — 봉투 · 고객 식별 · 인식 확정 · 장면 키프레임 · 가리킴 풀기 · 넘김 요약 · 멱등 대기열 · 채널별 형식 · 평가 · 실측 (OM1~OM8)

화면은 `/omni/inbox`(통합 받은 편지함) · `/omni/live`(실시간 음성 · 영상) · `/omni/eval`(옴니 평가), 코드는 `app/stages/omni/` 입니다. 실제 채널은 `POST /api/omni/webhook/{채널}` 로 그 채널의 웹훅을 그대로 보내고, 화면의 채널 흉내(`/api/omni/send`)도 같은 모양을 만들어 같은 길로 보냅니다.

```
웹훅 · 채널 흉내 → 봉투(누가 · 채널 · 글 · 첨부 · 보낸 시각 · 외부 id) (OM1)
  → 고객 식별(같은 주소 · 같은 전화번호) → 열린 세션에 이어 붙임 (OM1)
  → 대기열 받기: (채널, 외부 id) 멱등 · 보낸 시각 순서 · 실패하면 다시 (OM6)
  → 사진 · 영상 프레임: 장면이 바뀌었을 때만 비전 읽기 → 세션 시간축 색인 (OM3)
  → 말 + 장면 융합: '이거' → 지금 장면, '아까' → 앞 장면 (OM4)
  → 서비스 답변(입력 방어 · 검색 · 근거 격리 · 검증 · 요청 기록) + 그 프레임 사진
  → 채널별 형식 · 개인정보 (OM7) → 전달(멱등)
채널 바꿈 → 넘김 요약 · 미해결 질문 · 새 채널의 첫 말 (OM5)
말하는 도중 → 연속 일치 확정 → 문장 끝이 확정되면 미리 검색 (OM2)
재기 → 시나리오(맥락 · 중복 · 형식 · 지연 · 일관성) · 대기열 훈련 · 키프레임 채점 (OM8)
```

## 설계

- **어댑터는 봉투만 만든다(OM1).** 채널마다 봇을 따로 두면 고객이 채팅에서 한 설명을 전화에서 다시 해야 합니다. 채널 모양을 아는 곳은 어댑터(`envelope.normalize`) 하나이고, 그 뒤의 대기열 · 융합 · 답은 채널을 모릅니다. 어댑터 모양은 흔한 메신저 · 문자 · 이메일 웹훅의 일반적인 필드 구성(메시지 id · 보낸 사람 · 본문 · 첨부)을 따라 새로 정했고, 실제 서비스에 붙일 때는 필드 이름만 맞추면 됩니다. 이메일은 인용된 앞 메일 · 서명을 떼고, 전화 · 영상은 웹훅이 아니라 확정된 발화 단위(통화 id + 순번)로 들어옵니다.
- **추측으로 묶지 않는다(OM1).** 같은 채널 주소면 같은 고객, 전화번호는 채널이 달라도(문자 · 전화 · 메신저 프로필 · 계정에 확인된 번호) 같은 고객입니다. 서로 다른 주소를 한 사람으로 묶는 것은 본인 확인 뒤 명시적으로만(`link`) 하고, 이미 다른 고객에 묶인 주소는 덮어쓰지 않습니다 — 잘못 묶으면 남의 상담 기록이 보입니다. 같은 고객의 열린 세션(마지막 활동 72시간 안)이 있으면 채널을 바꿔도 그 세션에 이어 붙습니다.
- **받기와 처리를 나눈다(OM6).** 웹훅은 제때 200 을 받지 못하면 같은 메시지를 다시 보냅니다. 받자마자 (채널, 외부 id) 로 기록하고, 이미 있으면 중복으로만 남깁니다. 처리는 같은 세션 안에서 보낸 시각 순서로 하고, 앞 메시지가 실패하면 뒤 메시지를 멈춥니다(건너뛰면 '문이 안 열려요' 보다 '그럼 어떻게 해요?' 에 먼저 답함). 세 번 실패하면 사람이 볼 수 있게 실패로 둡니다. 나가는 답에도 멱등 키(`reply:<받은 메시지 id>`)를 붙여, 처리를 다시 해도 답은 한 번만 나갑니다. 먼저 보냈는데 늦게 도착한 메시지는 '늦게 도착' 으로 표시합니다 — 이미 나간 답을 되돌리지는 않습니다.
- **고치기 전의 인식으로 검색하지 않는다(OM2).** 스트리밍 인식기는 더 들을수록 앞 인식을 고칩니다('세탁기 무늬' → '세탁기 문이'). 연속한 가설 N 개가 앞에서부터 같은 낱말만 확정하고(스트리밍 음성 인식에서 널리 쓰는 local agreement 규칙 — 설계만 참고해 새로 작성), 확정된 글이 문장 끝을 지나면 그 문장으로 검색을 먼저 시작할 수 있습니다. N=1 은 빠르지만 틀린 낱말을 확정하고, N=3 은 안전하지만 확정이 늦습니다 — 확정 오류 · 깜빡임 · 확정 지연(가설 수)으로 고릅니다.
- **장면이 바뀐 순간만 읽는다(OM3).** 프레임마다 비전 모델로 읽으면 한 장에 1~3초가 들어 실시간이 안 됩니다. 장면 변화는 두 기준으로 봅니다: 전체 변화(16×16 흑백 축소본의 평균 밝기 차 ≥ 6 — 멀티모달 수집과 같은 기준, 카메라를 돌림)와 국소 변화(48×48 축소본에서 밝기 차가 25 를 넘는 칸이 0.8% 이상 — 같은 표시창에서 코드만 바뀜). 평균 밝기 차만 보면 표시창 코드가 UE → dE 로 바뀐 시험 그림이 0.29 로 문턱에 한참 못 미쳐 장면을 놓쳤습니다. 칸 단위로 보면 1.0~1.5% 가 바뀌었고, 카메라 노이즈(±8) · 노출 변화(밝기 8%)는 그런 칸이 0% 였습니다. 바뀐 뒤 1초 안의 다음 변화는 같은 장면 전환으로 봅니다. 키프레임은 비전 LLM 으로 {설명 · 표시창 글자 · 코드 · 물체} 를 JSON 으로 읽고, 코드는 사진 진단(AS4)처럼 알려진 코드에 맞춥니다. 키프레임 사진은 서버 메모리에만 잠시(세션마다 40장) 두고, 남기는 것은 장면 설명(세션 메모리의 색인)뿐입니다 — 영상 통화 화면은 개인 영상입니다.
- **가리킴은 장면으로 푼다(OM4).** '이거 · 이게 · 여기 · 이 표시' 는 말한 순간(세션 시간축)의 장면, '아까 · 전에 · 처음' 은 색인의 앞 장면(질문 낱말과 겹치는 장면이 먼저)으로 풉니다. 장면에 코드가 있으면 질문에 넣고(코드로 매뉴얼 항목을 찾는 것이 가장 정확했음, AS4), 앞 채널에서 말한 제품도 넣습니다(코드는 제품마다 뜻이 다름). 영상 통화 중의 가리킴 없는 짧은 질문('어떻게 해요?')은 지금 장면을 맥락으로만 붙입니다. 바꿔 쓴 질문은 검색용이고, LLM 에는 원래 질문 + 장면 설명(시스템 지시) + 그 프레임 사진이 함께 갑니다 — 바꿔 쓴 말이 틀려도 사진으로 바로잡게.
- **넘길 것을 정해 둔다(OM5).** 넘김 요약은 LLM 없이도 만들어집니다: 사실(제품 · 코드 · 증상 · 이미 안내한 조치)은 대화 메모리(C3), 미해결 질문은 '답이 안 나갔거나 근거 없음으로 끝난 질문', 다음 할 일은 마지막 답의 단계입니다. LLM 의 한 문장 요약은 통화 요약 검증(VC7)처럼 기록과 글자 겹침으로 맞춰 보고, 맞지 않으면 규칙 요약을 씁니다. 새 채널의 첫 말은 앞 채널 이름 · 아는 사실 · 미해결 질문부터 꺼내 고객이 같은 설명을 반복하지 않게 합니다.
- **내용은 하나, 모양만 채널마다(OM7).** 채널마다 답을 따로 만들면 같은 질문에 채널마다 다른 내용을 답합니다. 검색 · 검증을 거친 답 하나를 채널 규칙으로 바꿉니다: 음성 · 영상은 두 단위(문장 또는 단계)까지 읽는 글(VC4)로 + '나머지 단계는 문자로 보내 드릴까요?', 문자는 70자 안에 링크 · 마크다운 · 근거 번호 없이(넘치면 첫 문장 + '자세한 안내는 채팅에서'), 메신저 · 카톡형은 단계 줄과 빠른 답장 버튼('N단계 했어요' · 늘 '상담원 연결' — 단계 글을 줄여 버튼을 만들면 '배수 필터를 여' 처럼 어미가 잘렸음), 이메일은 인사 · 맺음말 · 근거 각주, 웹 채팅은 마크다운 그대로입니다. 개인정보는 채널마다 다르게 가립니다 — 문자 · 메신저 · 음성(알림 미리 보기 · 스피커폰으로 남이 볼 수 있음)은 전화번호 · 이메일까지, 이메일 · 웹 채팅은 주민번호 · 카드 · 계좌만.
- **채널을 넘나드는 문제를 잰다(OM8).** 시나리오 6개(채팅 → 영상, 카톡형 재전송 → 문자, 전화 끊김 → 메신저, 이메일 → 채팅, 영상 앞 장면, 문자 개인정보)를 실제 웹훅 모양으로 같은 길에 보냅니다. 영상 걸음의 프레임은 오류 코드 화면 그림(사진 진단 시험 그림)입니다. 잼: 답에 필요한 표기 · 채널을 바꾼 걸음의 넘김 요약 · 첫 말에 앞 사실 · 같은 세션으로 이어졌나 · 재전송에 처리 · 답이 한 번만인가 · 형식 위반 · 첫 응답까지 지연이 채널 예산(음성 1.5초 · 영상 2초 · 채팅 4초 · 카톡형 5초 · 메신저 15초 · 문자 30초 · 이메일 10분) 안인가 · 같은 묶음 질문의 채널 간 핵심 표기(코드 · 모델 · 숫자) 일치. 대기열의 성질(재전송 · 순서 뒤섞임 · 일시 실패)은 LLM 없이 수백 건 훈련(`drill`)으로, 키프레임 고르기는 장면 길이를 아는 시험 영상(`score_keyframes`)으로 따로 잽니다.
