# 실시간 음성 상담 — 인식 · 턴 관리 · 짧은 지연 RAG · 합성 · 감정 · 상담원 보조 · 통화 요약 · 실측 (VC1~VC7)

화면은 `/voice/call`(음성 상담 통화) · `/voice/assist`(상담원 보조 · 통화 요약) · `/voice/eval`(음성 평가 · 지연 보고), 코드는 `app/stages/voice/` 입니다. 통화 한 건은 AS 상담 기록(`channel=voice`)과 짝을 이뤄 티켓 · 의미 캐시를 같이 씁니다.

```
마이크 → 16kHz PCM 조각(250ms) ─ 턴 관리: 말소리 감지 · 침묵 500ms = 끝점 후보 (VC2)
   ↓ 후보 조각만 인식(STT_URL · 로컬 Whisper, 앞 문맥 = 용어 사전) → 표기 복원(이 사 → E4) (VC1)
   ↓ 이어질 말로 끝나면 1.4초까지 더 기다림 · 아니면 고객 턴 → 감정(내용 + 목소리) (VC5)
   ├ 자동 응답: 안전 · 이관이면 고정 안내 + 티켓 / 의미 캐시 / 짧은 근거 → LLM 스트리밍 → 문장마다 개인정보 가림 → 읽는 글 → 합성 (VC3 · VC4)
   │     └ 소리가 나오는 동안 고객이 말하면 화면이 바로 멈춤 · 몇 글자까지 읽었는지 기록 (VC2)
   ├ 상담원 보조: 근거 3개 · 확인할 질문 → 추천 답 → 채택 · 고쳐서 씀 · 무시 (VC6)
   └ 종료: 전사 → 양식 요약 → 항목마다 전사와 일치 확인 → 해결 안 됐으면 티켓 (VC7)
턴마다 끝점 대기 · 인식 · 캐시 · 검색 · 첫 문장 · 첫 합성 시간을 예산(1200ms)과 비교 (VC3)
```

## 설계

- **조각으로 보내고 끝점에서만 인식.** 브라우저 MediaRecorder 의 webm 조각은 앞 조각 없이 풀 수 없어 스트리밍에 맞지 않습니다. 화면이 마이크 소리를 직접 16kHz 정수로 줄여 250ms 마다 보내고, 서버의 턴 관리가 끝점 후보를 낼 때 그 발화 조각만 인식합니다. 통화가 끝나기 전에 처리가 시작되고, 인식 횟수는 발화 수만큼입니다.
- **끝점은 침묵 + 글의 모양.** 침묵 500ms 면 '끝났을지도' — 인식해 본 글이 이어질 말('~는데' · '그리고' · '~고')로 끝나면 1.4초까지 더 기다립니다. 짧게 끊으면 생각 중인 고객의 말을 자르고, 길게 기다리면 응답이 늦어 한 문턱으로는 둘 다 맞출 수 없습니다. 말소리 문턱은 조용한 프레임으로 잡음 바닥을 따라갑니다(통화마다 배경 소음이 다름).
- **끼어들기는 화면에서 바로.** 소리가 나오는 동안 말소리가 200ms 이어지면 화면이 바로 멈춥니다 — 서버를 거치면 왕복 지연만큼 늦습니다. 서버에는 어느 턴을 몇 글자까지 읽었는지만 보내, 다음 답이 못 들은 안내를 다시 말할 근거로 남깁니다. 스피커 소리가 마이크로 되돌아오는 것은 브라우저 반향 제거에 맡깁니다.
- **용어 사전 두 겹.** 인식기 앞 문맥에 컬렉션의 제품 모델 · 오류 코드를 주고(Whisper 는 앞 문맥의 표기를 따라 적는 경향), 받아 적은 소리를 표기로 복원합니다 — 고객은 'E4' 를 '이 사', 'WM-200' 을 '더블유엠 이백' 으로 말하고 인식기는 소리대로 적습니다. 사전에 실제로 있는 표기로만 바꾸고, 짧은 코드는 코드를 말하는 문맥(오류 · 떠요 · 표시)일 때만 바꿉니다('다음 주에 이사 가요' 가 망가지지 않게).
- **지연 예산부터 나눈다.** 말이 끝난 뒤 첫 소리까지 1200ms(설정)를 끝점 대기 34% · 인식 17% · 캐시 · 검색 8% · 첫 문장 29% · 첫 합성 12% 로 나누고, 턴마다 실측을 예산과 비교해 넘은 단계를 남깁니다. 보고 화면은 통화 기록에서 단계별 p50 · p95 와 예산 안 비율을 모읍니다 — 무엇을 고칠지 알려면 단계별로 봐야 합니다(서빙 실측: 질문당 시간의 2/3 가 근거 읽기).
- **음성 답은 설정이 다르다.** 의미 캐시(AS3)를 먼저 보고, 없으면 근거 2개 · 900자 · 2~3문장 · 첫 문장에 핵심 조치로 서비스 답변 단계(입력 방어 → 검색 → 근거 격리 → LLM → 검증 → 요청 기록)를 그대로 탑니다. 첫 문장만 들어도 쓸모 있게 하려는 것입니다.
- **먼저 말하고 나중에 고친다.** 소리는 전체 검증보다 먼저 나갑니다. 그래서 문장이 완성된 뒤 · 읽기 전에 개인정보만 바로 가리고(소리로 새지 않게 막을 수 있는 마지막 자리), 근거 일치 · 출력 정책 결과는 턴에 남겨 상담원 화면 · 보고에서 봅니다. 검증을 통과한 답만 캐시에 넣어, 같은 질문의 다음 답은 검증된 글로 바로 나갑니다.
- **읽기 규칙.** 합성기는 'E4' 를 '이 포' 로, 'WM-200' 을 '더블유엠 마이너스 이백' 으로 읽습니다. 코드는 한 글자씩(이 사), 모델 번호는 자릿값(이백), 전화번호는 한 자리씩, 단위는 한국어로(30℃ → 삼십 도), 번호 목록은 '첫 번째', 근거 번호 · 마크다운은 읽지 않습니다. 합성 서버(TTS_URL)가 없으면 화면이 브라우저 음성(ko-KR)으로 같은 '읽는 글'을 읽습니다.
- **감정은 내용 + 목소리 변화.** 내용은 불만 표현 규칙(턴마다 LLM 판정은 너무 느림), 목소리는 같은 통화 첫 발화 대비 크기 · 높이 · 말 속도 변화만 봅니다(원래 큰 목소리를 화났다고 보지 않게). 이관: 상담원 요청 · 강한 불만 · 불만 두 턴 이어짐 · 같은 문제 세 번 · 안전 문의. 이관 전에도 불만이면 말투 지시(공감 · 사과 · 한 가지 조치)를 시스템 프롬프트에 붙입니다. 강한 표현 하나의 가중치는 라벨 문장 38개로 보정했습니다(0.55 → 0.75, 그 전에는 강한 불만 6개를 놓침) — 같은 세트로 잰 값은 보정 결과라 실측은 다른 문장으로 잽니다.
- **상담원 보조가 먼저.** 완전 자동 음성 상담은 이 PC 에서 지연 · 정확도 모두 어렵지만, 상담원 보조는 사람이 최종 판단을 해 몇 초 늦어도 쓸모가 있습니다. 근거를 먼저 띄우고(검색만), 추천 답은 그 뒤에. 확인할 질문은 상담에 빠진 정보에서 나옵니다: 모델 모름 · 사전에 없는 코드 · 안전 증상 · 해 본 조치 모름. 상담원이 누른 결과로 채택률을 의도별로 잽니다.
- **요약은 전사로 검증.** 양식(문의 · 제품 · 코드 · 진단 · 안내한 조치 · 해결 · 약속 · 다음 할 일)을 LLM 이 채우고, 모델 · 코드 · 날짜는 전사에 같은 표기가 있는지, 문장 항목은 글자 3-gram 이 한 발화와 40% 이상 겹치는지 봅니다. 맞지 않는 항목은 '확인 필요'로 표시합니다. 통화를 만들 때 받은 제품 모델(고객 기록)은 '통화 정보'로 채웁니다.
- **음성은 개인정보.** 전사는 기본으로 개인정보를 가려 저장하고(`VOICE_STORE_RAW`), LLM 에도 가린 글이 갑니다(제품 · 코드는 가리지 않음). 통화 기록은 `VOICE_RETENTION_DAYS`(기본 30일) 뒤 지웁니다. 다만 이름은 G2 탐지(규칙)가 잡지 못합니다 — 이름이 섞인 전사는 그대로 남을 수 있어, 고객 정보는 통화 정보 항목으로 따로 받는 것이 안전합니다.
