# 데이터 분석 · Text-to-SQL — 분석 자료 · 스키마 연결 · 의미 계층 · 실행 검증 · 해석 · 권한 · 실행 정확도 · 실측 (DA1~DA7)

화면은 `/analytics/ask`(자연어로 데이터 묻기) · `/analytics/semantic`(지표 정의 · 권한) · `/analytics/eval`(실행 정확도), 코드는 `app/stages/analytics/` 입니다.

```
분석 자료(별도 SQLite 파일: 예시 AS 자료 · 앱 기록의 분석용 열만)
   ↓ 스키마 카드(표 · 열 설명 + 예시 값, 개인정보 열 제외) → 질문 낱말과 연결 → 관련 표 + 외래 키 표 (DA1)
   ├ SQL 생성(연결한 스키마 · 예시 · 방언) (DA3)            └ 의미 계층: LLM 은 {지표 · 차원 · 필터 · 기간} JSON → 규칙으로 SQL (DA2)
   ↓ 가드(글 검사 → 읽기 전용 → 허가 콜백 → 시간 · 행 상한) (DA6)
   ↓ 실행 검증: 오류 · 막힘 · 빈 결과 · 상식 밖 값 → 그 사실을 붙여 다시 (DA4)
   ↓ 해석: 결과 표 → 문장 · 막대, 답의 수가 결과에 있나 (DA5)
   └ 실행 정확도: 정답 SQL 의 결과와 같은가 — 유형별 · 방식별 (DA7)
```

## 설계

- **앱 DB 를 직접 열지 않는다.** 앱 DB 에는 고객 이름 · 대화 원문 · 해시 사슬 기록이 함께 있습니다. LLM 이 만든 SQL 을 거기에 돌리면 읽기 전용이어도 개인정보 열을 읽을 수 있고, 무거운 질의가 서비스를 느리게 합니다. 분석에 필요한 열만 옮긴 파일(`data/analytics/<이름>.db`)을 만들어 읽기 전용으로 엽니다. 예시 자료(demo)는 정해진 씨앗으로 만든 AS 접수 자료(제품 5 · 문의 2,000 · 티켓)이고 날짜는 2026-04-01 ~ 2026-09-30 고정입니다 — 평가 질문의 정답이 '지난달' 같은 상대 날짜에 기대지 않고 언제 돌려도 같습니다. 분포에 일부러 차이를 둡니다(WM-200 E4 가 많음 · 건조기 만족도가 낮음 · 9월에 접수가 늚). 앱 기록(app…)은 AS 상담 · 요청 기록의 분석용 열만 옮깁니다.
- **스키마 카드에 예시 값.** 열 이름만으로는 값의 모양을 모릅니다(code 열의 값이 'E4' 인지 '4' 인지, 종류가 '건조기' 인지 'dryer' 인지). 글자 열마다 자주 나오는 값 5개를 실제 자료에서 뽑아 넣습니다. 개인정보 열은 예시 값을 뽑지 않고, 권한이 없는 역할에게는 열 자체를 보이지 않습니다 — 보이면 LLM 이 쓰려다 막힙니다.
- **연결은 규칙으로.** 질문 낱말 → 동의어 사전 · 열 설명 · 예시 값 겹침으로 표 · 열 점수를 매기고, 상위 표와 외래 키로 이어진 표만 넣습니다. 이 자료는 표가 셋이라 전체 스키마도 맥락에 들어가므로, '연결 없이 전체 스키마' 방식과 같은 질문으로 비교해 연결이 정확도를 떨어뜨리지 않는지(연결 재현율 — 정답 SQL 의 표를 모두 골랐나) 봅니다.
- **지표는 정의로(의미 계층).** '재방문율'을 LLM 이 매번 다르게 해석하면 같은 질문에 다른 숫자가 나옵니다. 지표 6개를 SQL 식으로 고정하고, LLM 은 지표 · 차원 · 필터 · 기간을 JSON 으로 고르기만 합니다. SQL 은 정해진 규칙으로 만들고, 정의에 없는 지표 · 차원 · 필터면 SQL 을 만들지 않습니다(지어낸 지표를 실행하지 않음). 정의 밖의 질문(특정 날짜 · 상위 1개 날짜 등)은 의미 계층으로 답할 수 없어 정확도가 낮게 나오는 것이 정상입니다 — 직접 SQL 생성과 함께 보는 이유입니다.
- **실행 결과로 검증하고 고친다.** 문법이 맞는 SQL 도 틀린 숫자를 냅니다. 읽기 전용으로 실행해 SQL 오류 · 막힘 · 빈 결과 · 상식 밖 값(건수 열의 음수 · 비율 열이 100 초과 · 열이 모두 NULL)이면 그 사실을 붙여 다시 만듭니다(기본 3번). 빈 결과는 조건에 맞는 것이 정말 없을 수도 있어 한 번만 다시 묻습니다. Text2Cypher 실측에서 실행 검증 재시도로 정확 일치가 40 → 53% 로 오른 것과 같은 방식입니다.
- **숫자는 결과에서만.** 결과 표를 2~3문장으로 바꿀 때 LLM 이 숫자를 바꾸거나 지어낼 수 있습니다. 답 글의 수가 결과 표의 수(소수 첫째 자리 · 정수 반올림, 0~1 비율의 백분율)나 질문의 수인지 검사하고, 아니면 '결과에 없는 수'로 표시합니다(장기 실행의 지어낸 숫자 검사와 같은 원칙). 차트는 '이름 열 하나 + 수 열 하나 · 2~30행' 일 때만, CDN 없이 표 안의 `<progress>` 막대로 그립니다.
- **권한은 실행하는 쪽에서.** 프롬프트로 'DELETE 하지 말라'고 하는 것은 방어가 아닙니다. 겹겹이 막습니다: (1) 글 검사 — 문 하나 · SELECT/WITH 시작 · 금지 낱말(문자열 안의 낱말은 보지 않음), 빨리 거절하고 이유를 알리려고 (2) 읽기 전용 URI + `PRAGMA query_only` (3) SQLite 허가 콜백 — 읽기 외 동작 거부, 역할에 막힌 열(개인정보)을 읽으면 거부. 별칭 · 하위 질의 · `SELECT *` 로 돌아가도 실제로 읽는 열에서 잡힙니다 (4) 시간 상한(진행 콜백) · 행 상한. 관리자 역할은 화면에서 고른 값을 믿지 않고 서버가 확인한 관리자만 씁니다. 위험 질의 14개(삭제 · 두 문 이어 붙이기 · ATTACH · PRAGMA · 개인정보 열 4가지 · 무한 재귀 · 정상 질의 3개)로 막혀야 할 것이 막히고 정상 질의는 통과하는지 시험합니다.
- **실행 정확도.** 만든 SQL 과 정답 SQL 의 실행 결과를 비교합니다 — SQL 글자가 달라도 결과가 같으면 맞습니다. 순서가 의미 있는 질문(상위 N · 월별)만 행 순서까지 보고 나머지는 행 묶음으로, 수는 소수 둘째 자리로 맞추고, 설명 열을 더 붙인 답은 정답 열이 같은 순서로 들어 있으면 맞다고 봅니다. 유형(집계 · 날짜 · 조인 · 비율 · 상위 · NULL)별로 모아 어디서 틀리는지 봅니다.
