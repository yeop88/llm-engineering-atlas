# 규제 대응 — 규제 자료 · 적용 규제 · 조항-통제 그래프 · 감사 · 실측 (RC1~RC8)

화면은 `/compliance/scope`(적용 규제 · 위험 등급) · `/compliance/controls`(조항-통제 매핑 · 개정 감시) · `/compliance/records`(처리 근거 · 결정 기록 · 검토 요청) · `/compliance/audit`(영향 평가 · 통제 감사), 코드는 `app/stages/compliance/` 입니다. 기준 자료(규제 목록 · 서비스 기능 · 적용 규칙 · 통제 · 등급 기준표 · 의무 질문)는 `app/stages/compliance/presets/` 의 JSON 파일입니다. **기술 설계를 위한 정리이며 법률 자문이 아닙니다.**

```
국가법령정보 API ─ 시행일별 판 ─ 규제 자료 컬렉션(법령마다 한 판)
   │                                   │
   │            RC1 기능 특성 → 적용 규칙(조항 · 의무 요지 · 통제) ── 조항 원문
   │            RC2 기준표 점수 → 등급 제안 → 사람이 확정
   │                                   │
   └─ 현행 · 시행예정 판 ─ 조항 비교 ─ RC7 조항-통제 그래프(통제 -근거→ 조항, 기능 -적용→ 통제) → 영향받는 통제 · 기능
                                       │
RC3 처리 목록 · 보관 기한 · RC4 결정 기록(요청 기록에서) · RC6 AI 응답 고지 · 사람 검토 요청
                                       │
RC5 측정 기록으로 영향 평가 초안 → 사람이 승인 · RC8 통제마다 증적을 기록에서 모아 감사
```

## 설계

- **규제 자료는 API 원문, 법령마다 한 판.** 처음에는 이미 받아 둔 법률 데이터셋(`smhilee/korean-law-dataset`)을 쓰려 했는데, 이 데이터셋은 조문 가지번호를 버려 '제37조의2(자동화된 결정에 대한 정보주체의 권리 등)'가 '37'로 들어가 제37조와 섞이고, 개인정보 보호법 조항이 **126개가 아니라 76개**만 남습니다(가지번호 조항 50개가 사라짐). 판도 하나뿐이고(2023-09-15 시행판), 인공지능 기본법(2026-01-22 시행)은 아예 없습니다. 규제 대응은 '어느 판의 어느 조항'이 핵심이라 국가법령정보 공동활용 API(`app/stages/compliance/lawapi.py`)로 시행일별 판을 받습니다(키 `LAW_API_OC` 는 open.law.go.kr 에서 신청한 이메일 아이디). 조문은 공개 자료 가져오기와 같은 줄 모양('제N조(제목) / ① 항 / 1. 호 / 가. 목')으로 바꿔 법령 청킹 · 조문 번호 조회 · 지식 그래프 정형 추출이 그대로 동작합니다. 한 컬렉션에 같은 법령의 두 판을 넣지 않습니다 — 개정 전후 조항이 한 검색 결과에 섞이면 이미 바뀐 의무를 근거로 통제를 만들게 됩니다(맵 원칙).
- **RC1 규칙이 먼저, 검색은 후보로.** '이 기능에 이 조항이 적용된다'는 근거를 댈 수 있어야 해서 적용 판단은 규칙 파일(`presets/rules.json`, 15개)로 합니다: 기능 특성(생성형 AI · 개인정보 · 민감정보 · 자동화된 결정 · 고영향 영역 · 기록 보관)이 모두 맞으면 조항 · 의무 요지 · 통제가 붙습니다. 의무 요지는 현행판 원문을 읽고 줄였고, 화면은 원문을 함께 보입니다. 검색은 규칙이 놓친 조항을 '검토할 후보'로만 보입니다 — 비슷한 조항이 나왔다고 적용된다고 볼 수는 없습니다.
- **RC2 점수는 제안, 확정은 사람.** 기준표(결정의 영향 · 사람의 개입 · 데이터 민감도, 각 1~3) 합이 8 이상이면 높음, 6 이상이면 중간. 고영향 영역(인공지능 기본법 제2조제4호: 채용 · 대출 심사 · 보건의료 등)은 점수와 상관없이 높음입니다 — 사람이 매번 확인하더라도 법이 고영향으로 봅니다. 제안과 다르게 정하면 이유를 받고, 관리자가 확정하면 확정한 사람이 남습니다(`compliance_records`, 마이그레이션 0013).
- **RC3 처리 목록은 이미 있는 것을 모은다.** 컬렉션(문서 수 · 출처 · 라이선스) · 요청 기록 · 고객 프로필 · AS 대화를 한 목록으로 보이고, 대상마다 처리 목적 · 근거 · 보관 일수 · 담당을 등록합니다(개인정보 보호법 제30조 처리방침의 '처리 목적 · 보유 기간 · 파기 절차'에 옮길 수 있는 모양). 파기는 되돌릴 수 없어 관리자 · `confirm=true` 로만, 컬렉션 문서는 청크 · 벡터까지 지웁니다.
- **RC4 설명은 기록에서.** 결정 기록은 새로 남기지 않고 요청 기록(근거 문서 · 문장별 검증 · 조문 인용 검사 · 가드레일 조치 · 모델 · 단계)을 한 장으로 엮습니다. 그 행의 해시를 다시 계산하고 앞 행과의 이음을 확인해 '이 기록은 고쳐지지 않았다'를 함께 보입니다(`tracing.check_row`). 남의 질문 원문은 관리자만 봅니다.
- **RC6 고지는 답 글과 따로.** 서비스 답변(`app/pipeline/serve.py`)이 AI 응답 고지(`AI_NOTICE`, 인공지능 기본법 제31조 사전 고지 · 생성물 표시)를 답 글에 섞지 않고 `notice` 로 따로 돌려주고, 고지했는지를 요청 기록(`guard.notice`)에 남깁니다. 답 글에 섞으면 검증(근거 일치)이 고지 문장을 '근거 없는 문장'으로 세고, 캐시한 답에는 빠집니다. 답변 화면 네 곳(RAG 답변 · AS 상담 · 대화 상담 · GraphRAG)은 공용 부품 `ui.aiNotice` 로 같은 자리에 고지와 '사람 검토 요청' 버튼을 보입니다 — 화면마다 따로 붙이면 한 곳만 빠져도 요청 길이 끊깁니다. 7일 넘게 열린 요청은 감사에서 실패입니다.
- **RC5 영향 평가는 측정 기록으로.** 새로 돌리지 않고 최근 검색 평가 · 레드팀 · 대화 평가 · 드리프트와 근거 자료 속 개인정보를 run 번호와 함께 모아, 전체보다 0.10 이상 낮은 질문 유형과 통과 못 한 공격 유형을 '약한 집단'으로 짚습니다. 평균이 좋아도 특정 유형에서 크게 실패하기 때문입니다. 저장할 때 증적을 서버에서 다시 모아 그 순간의 값으로 남깁니다(화면이 보낸 숫자를 믿지 않음).
- **RC7 조항-통제 그래프.** 조항 노드는 법령 문서에서 지식 그래프 정형 추출(K3, `kg.extract.statute`)로 만들고, '통제 -근거→ 조항'(규칙) · '기능 -적용→ 통제'를 그래프 저장소(K5)에 잇습니다. 시행령 조문의 '법 제N조' 참조(REFERS_TO)도 함께 들어와, 시행령 조항이 바뀌면 모법 조항을 거쳐 통제를 찾습니다. 개정 감시는 자료의 판을 API 의 현행 · 가장 가까운 시행예정 판과 조항별로 비교하고(띄어쓰기 · `<개정 …>` 표시는 무시 — 표시만 붙은 조항을 '바뀜'으로 세지 않게), 바뀐 조항 키를 그래프에 넣어 영향받는 통제 · 기능을 돌려줍니다.
- **RC8 감사는 통제가 아니라 증적을 센다.** 통제 15개마다 증적을 기록에서 모읍니다: 최근 서비스 답 200건의 고지 · 개인정보 · 근거, 해시 사슬, 레드팀 최근 실행(90일 안, 공격 방어 ≥ 0.9, 정상 질문 모두 통과), 보관 기한, 사람 판단 기록. 결과는 통과 · 실패 · 부분 · 없음(통제 자체가 없음) · 수동(기록으로 확인할 수 없음)으로, LLM 없이 돌아 `WATCH_AUDIT_HOURS` 마다 앱이 다시 돕니다.

## 실측 (2026-10-21)

자료는 국가법령정보 API 로 받은 **2026-01-22(인공지능 기본법 시행일) 기준 판**입니다 — 인공지능 기본법 · 시행령(2026-01-22 판), 개인정보 보호법 · 시행령(2025-10-02 판), 조항 343개. 청킹은 법률 컬렉션과 같은 `legal 800/100, merge_below 200`(청크 362개), 색인은 임베딩 모델 #23(인덱스 #14, 1024차원, 292초). 일부러 지난 판을 넣은 이유는 개정 감시를 실제 개정으로 재려는 것입니다.

### RC7 개정 감시 — 실제 개정으로

| 법령 | 자료의 판 → 현행 | 바뀜 · 새로 생김 | 영향받는 통제 |
|---|---|---|---|
| 인공지능 기본법 | 2026-01-22 → 2026-07-21 | 4 · 2 (제3조 · 제6조 · 제18조 · 제35조 / 제17조의2 · 제22조의3) | 영향 평가 승인 기록 |
| 인공지능 기본법 시행령 | 2026-01-22 → 2026-08-20 | 5 · 6 | 위험 등급 검토 기록 · 영향 평가 승인 기록(시행령 제28조 → 법 제35조 참조로) |
| 개인정보 보호법 | 2025-10-02 → 2026-09-11 | 16 · 1 (제23조 · 제29조 · 제34조 등 / 제30조의3) | 개인정보 가리기 · 문서 권한 · 요청 기록 · 위변조 검출 · 인젝션 방어 · 유출 통지 절차 |
| 개인정보 보호법 시행령 | 2025-10-02 → 2026-09-11 | 23 · 2 | 보관 기한 · 처리 근거 등록 · 정보주체 열람 · 삭제 등 9개 |

정답은 감지와 따로 만들었습니다: 현행판 원문의 개정 표시(`<개정 2026.3.10>` 등)가 옛 판 공포일보다 뒤인 조항 = 그사이 바뀐 조항. 개인정보 보호법 16/16, 시행령 23/23, 인공지능 기본법 시행령 5/5 를 모두 감지했고, 감지에만 있는 것은 모두 새로 생긴 조항(표시가 `[본조신설]` 이라 개정 표시 정답에 안 잡힘)이었습니다. 인공지능 기본법은 2026.1.20 개정 하나가 조문마다 다른 날 시행돼(일부 1/22, 나머지 7/21) 개정 표시만으로는 판을 가를 수 없어 따로 확인했습니다 — 2026.1.20 표시가 있는 조항 12개 중 9개는 1/22 판에 이미 들어 있었고(그래서 '바뀜'이 아닌 게 맞음), 감지한 제3조 · 제18조 · 제35조가 7/21 에 시행된 부분, 제6조는 7/21 에 한 번 더 바뀐 조항입니다. 처음 시도한 조문별 시행일(`조문시행일자`)은 판의 시행일이 모든 조문에 같이 찍혀 정답으로 쓸 수 없었습니다.

시행예정 판도 함께 봅니다 — 개인정보 보호법은 2027-07-01 판에서 제28조의12~15 가 새로 생기고 19개 조항이 바뀝니다(실측 시점 기준 예정).

### RC1 의무 → 조항 검색

의무를 평이하게 물은 질문 22개(정답 조항은 현행판 원문을 읽고 정함, `presets/obligation_queries.json`), 조항 단위(한 조항의 청크 여럿은 한 번):

| 검색 | hit@1 | hit@3 | hit@10 | MRR |
|---|---|---|---|---|
| BM25 (#345) | 77.3% | 81.8% | 90.9% | 0.811 |
| 혼합 BM25 + 의미 (#346) | 77.3% | 90.9% | **100%** | 0.854 |

- 처음 잰 값(#342 BM25 hit@10 86.4% · #343 혼합 95.5%)은 채점이 틀렸습니다: 청크의 **첫 조문 머리만** 조항으로 셌는데, 짧은 조문이 이웃과 합쳐져(merge_below) 청크 362개 중 40개에 조항이 둘 이상 들어 있었습니다. '통계 작성을 위한 가명정보'(제28조의2)는 '제28조 + 제28조의2' 청크에 있어 두 검색 모두 영영 못 찾았습니다. 청크 안의 머리를 모두 보게 고친 값이 위 표입니다(`scope.chunk_articles`).
- 혼합이 BM25 보다 hit@10 +9.1%p — BM25 가 10위 안에서 못 찾은 '상담 기록 파기'(제21조) · '자기 정보 열람'(제35조)을 의미 검색이 7위 안으로 올렸습니다. 다만 hit@1 은 같습니다: 1위를 놓친 5개는 비슷한 조항이 먼저 나온 경우입니다(예: '보유 기간을 처리방침에' → 제21조 파기가 제30조 처리방침보다 먼저, '가명정보' → 같은 청크의 제28조가 제28조의2 보다 먼저).
- 그래서 적용 판단을 검색에 맡기지 않고 규칙으로 합니다. 검색은 규칙이 놓친 조항 후보를 보이는 데 씁니다.

### RC8 통제 감사 — 처음 상태 → 흐름을 거친 뒤

| | 처음 (#347) | 흐름을 거친 뒤 (#348) |
|---|---|---|
| 통과 · 부분 · 실패 · 없음 · 수동 | 7 · 1 · 5 · 1 · 1 | 8 · 4 · 1 · 1 · 1 |
| AI 응답 고지 | 실패 — 최근 서비스 답 54건 중 고지 기록 0 | 부분 — 60건 중 6건(고지 기능 뒤의 답은 모두 고지) |
| 처리 근거 등록 | 실패 — 컬렉션 7개 모두 미등록 | 부분 — 4개 미등록 |
| 위험 등급 · 영향 평가 | 실패 · 실패 | 통과(기능 5개 확정) · 부분(1개 승인) |
| 보관 기한 | 실패 — 요청 기록 보관 기한 없음(`TRACE_RETENTION_DAYS=0`) | 실패(그대로) |
| 개인정보 · 권한 · 인젝션 · 위변조 · 결정 기록 | 통과 | 통과 |
| 유출 통지 절차 | 없음 | 없음 |

'흐름을 거친 뒤'는 서비스 답 6개(대화 상담)와, 화면에서 사람이 할 일 — 위험 등급 확정 5 · 처리 근거 등록 3 · 영향 평가 승인 1 · 검토 요청 1건 처리 — 을 **실측용으로 API 로 대신 넣은 것**입니다(검토 요청 · 영향 평가 · 처리 근거 기록에 '실측'이라고 적음). 감사가 실제 운영 상태를 바꾸는 것은 이 입력들이고, 감사는 그 증적을 그대로 읽는다는 것을 보이려는 측정입니다.
