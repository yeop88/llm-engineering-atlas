# 문서 검색 (RAG)

임베딩 모델을 실제 업무 문서 검색에 쓰기 전에, **청킹 전략 × 임베딩 모델 × 벡터 DB × 검색 방식 × 리랭커** 조합을 직접 만들어 비교하는 기능입니다. 메뉴의 **문서 검색**에서 시작합니다.

```
문서 업로드 → ② 청크 세트(청킹 전략) → ③ 벡터 인덱스(임베딩 모델 + 벡터 DB) → ④ 검색 비교(의미/BM25/하이브리드 + 리랭커)
```

## 1. 컬렉션과 문서

- **컬렉션**은 문서 묶음입니다. 도메인(사내 문서 · 법률 · 고객·AS 문의 · 제품·매뉴얼 등)별로 만듭니다. 법률 도메인은 청킹 기본값이 "법률 구조"로 바뀝니다.
- 지원 형식: **PDF · DOCX · HWP(5.x) · HWPX** · TXT · MD · HTML · CSV · TSV · JSON · JSONL (파일당 기본 100MB, `MAX_UPLOAD_MB`)
  - HWP 는 바이너리 구조를 직접 읽습니다(외부 프로그램 불필요). 같은 문서 기준으로 PDF 보다 깨끗하게(목차 점선 등 잡음 없음), 약 100배 빠르게 추출됩니다.
  - 배포용(보호) HWP 는 본문이 암호화되어 미리보기 텍스트만 읽습니다. 암호 문서는 지원하지 않습니다.
  - 스캔 PDF 는 텍스트가 없어 OCR 이 필요합니다(업로드 시 경고).
  - 표는 셀을 ` | ` 로 이어 텍스트로 넣습니다(DOCX). HWP·HWPX 표는 셀이 줄 단위로 들어갑니다.
- 같은 내용의 파일(SHA-256 동일)은 자동으로 건너뜁니다.
- 원문은 페이지(PDF 쪽 / HWP 구역) 단위로 보관하므로, 청킹 전략을 바꿔 언제든 다시 나눌 수 있습니다.

## 2. 청크 세트 (청킹 전략)

| 방법 | 동작 | 언제 |
|---|---|---|
| **재귀 분할** (기본) | 문단 → 줄 → 문장 → 단어 순으로 큰 경계부터 잘라 길이에 맞춤 | 대부분의 문서 |
| **고정 길이** | 정해진 글자 수 + 겹침, 공백에서 끊음 | 구조 없는 텍스트(로그·OCR) |
| **문장 단위** | Kiwi 형태소 분석기로 한국어 문장을 나눈 뒤 묶음, 겹침은 문장 수 | 문장이 잘리면 안 되는 문서 |
| **법률 구조** | 법령은 조문(제N조, 제N조의N)·항(①②) 단위, 판결문은 【주문】【이유】【판시사항】 등 구획 단위. 각 청크에 소속 조문 제목 기록 | 법령 · 판례 · 계약서 |
| **페이지** | PDF 쪽 / HWP 구역 단위(너무 길면 재귀 분할) | 쪽 번호 인용이 중요한 문서 |

- 크기·겹침 단위는 **글자 수**입니다(한국어는 대략 1~1.5글자 ≈ 1토큰). 임베딩 모델의 최대 입력 길이보다 작게 잡으세요.
- **"임베딩할 때 문서 제목·조문 제목 붙이기"**를 켜면(기본) 인덱싱할 때 `문서 제목 · 조문 제목\n청크` 형태로 맥락을 붙여 임베딩합니다. 청크 원문은 그대로 보관합니다.
- **미리보기**로 청크 수, 길이 분포(히스토그램), 예시를 보고 정한 뒤 만듭니다. 만들 때 각 청크의 형태소(BM25 용)도 함께 저장합니다.
- 청크 세트를 만든 뒤 문서를 추가·삭제하면 **"문서 변경됨"** 표시가 붙습니다. 새 문서를 검색하려면 청크 세트를 다시 만드세요(문서 삭제는 자동 반영).

## 3. 벡터 인덱스

청크 세트 하나를 **임베딩 모델 + 벡터 DB (+ Matryoshka 차원)** 로 인코딩해 저장합니다. 같은 청크 세트로 여러 인덱스를 만들어 비교할 수 있습니다.

| 벡터 DB | 설정 | 특징 |
|---|---|---|
| **Qdrant** (기본) | `QDRANT_URL` 없으면 서버 없이 로컬 파일 모드(`data/qdrant`), 있으면 서버 | 필터·대규모·운영에 강함. 서버 대시보드 `http://localhost:6333/dashboard` |
| **PostgreSQL pgvector** | `PGVECTOR_URL` | ≤2000차원 `vector`+HNSW, ≤4000차원 `halfvec`+HNSW, 그 이상은 인덱스 없이 정확 검색(자동 선택). 문서 필터 시 반복 스캔(pgvector 0.8+) |
| **MariaDB VECTOR** | `MARIADB_URL` (11.7+) | `VECTOR(n)` + `VECTOR INDEX ... DISTANCE=cosine`. 기존 MariaDB/MySQL 인프라를 쓰는 경우 |

```bash
docker compose up -d                                          # Qdrant 서버 (선택 — 없어도 로컬 모드로 동작)
docker compose --profile pgvector --profile mariadb up -d     # pgvector(5433), MariaDB(3307) 추가
```

- 구축은 백그라운드 작업이며 진행률과 남은 시간을 보여 줍니다. 처음 쓰는 모델은 다운로드부터 합니다.
- 모든 저장소는 같은 점수(코사인 유사도)를 돌려주므로 서로 비교할 수 있습니다.
- 문서를 지우면 해당 청크의 벡터도 모든 인덱스에서 지웁니다.

### 검색 정확도 정책 (정확 검색 / 근사 검색)

HNSW 같은 근사 인덱스는 빠른 대신 가까운 벡터를 **놓칠 수 있습니다**. 이 앱은 검색 설정을 비교·평가하는 도구라서, 근사 오차가 평가 결과를 오염시키면 안 됩니다.

| 인덱스 벡터 수 | 검색 방식 | 설정 |
|---|---|---|
| `VECTOR_EXACT_MAX` 이하 (기본 20,000) | **정확 검색** — Qdrant `exact=True`, pgvector 인덱스 스캔 끔, MariaDB 인덱스 우회 | 수만 개까지는 전수 비교도 수십 ms 안팎 |
| 그보다 많음 | 근사 검색, 탐색 폭 `max(VECTOR_EF_SEARCH, top_k × 4)` (기본 200) | 값을 키우면 정확하지만 느림 |

**왜 생겼나 — 실제 사례 (2026-10-18)**: MariaDB HNSW 를 기본 탐색 폭(`mhnsw_ef_search=20`)으로 쓰던 때, 공공문서 컬렉션에서 관세청 보도자료의 청크 묶음(1~6번)을 인덱스가 **통째로 놓쳤습니다**. 같은 벡터로 정확히 계산하면 1~6위인 청크들입니다. 평가 세트 24문항의 상위 10개 재현율이 pgvector 1.000 에 비해 MariaDB 는 0.792(최소 0.00)였고, 그 결과 MariaDB 에 인덱스를 만든 KURE-v1 이 "이 문서에서 가장 나쁜 모델"로 잘못 측정됐습니다(직접 sentence-transformers 로 재면 정상). 이후 위 정책을 모든 저장소에 적용하고, 실제 임베딩처럼 한 방향으로 쏠린 데이터에서 정확 검색 결과와 일치하는지 확인하는 계약 테스트를 추가했습니다(`tests/test_vectorstores.py`). 저장소마다 결과가 다르면 인덱스 모델이 아니라 저장소부터 의심하세요.

## 4. 검색 비교

최대 4개 설정을 나란히 실행합니다. 설정은 브라우저에 컬렉션별로 저장됩니다.

| 항목 | 설명 |
|---|---|
| **방식** | 의미 검색(벡터) / BM25(형태소 키워드) / **하이브리드**(둘을 합침) |
| **합치기** | **RRF**(순위 기반, 점수 척도가 달라도 안정적 — 권장) / 가중합(점수 정규화 후 `α·의미 + (1−α)·BM25`) |
| **검색 후보** | 각 방식에서 가져올 후보 수(기본 50) |
| **리랭커** | 상위 후보(기본 30)를 Cross-Encoder 로 질의와 함께 다시 읽어 재정렬. 느리지만 정확도가 크게 오름 |
| **결과 수** | 최종으로 보여 줄 개수 |

결과마다 의미·BM25 순위와 점수, 리랭크 전 순위, 문서·쪽·조문 제목, 질의 형태소 하이라이트, 단계별 소요 시간(모델 로드 · 질의 임베딩 · 벡터 검색 · BM25 · 리랭킹)이 나옵니다.

### BM25 (한국어)

[Kiwi](https://github.com/bab2min/kiwipiepy) 형태소 분석으로 명사·동사/형용사 어간·어근·외국어·숫자만 남겨 색인합니다("공문서는 한글로 작성하여야" → `공문서 한글 작성`). 조사·어미 차이에 강하고, 법령 조문 번호나 제품 모델명처럼 **정확히 일치해야 하는 키워드**를 의미 검색이 놓칠 때 보완합니다.

### 리랭커

모델 화면의 종류 필터에서 "리랭커"로 볼 수 있습니다(BGE Reranker v2 M3, 한국어 파인튜닝판, Qwen3-Reranker 0.6B/4B, mxbai-rerank-v2, Nemotron Rerank 등). 입력 길이는 기본 1024토큰으로 제한합니다(`RERANKER_MAX_LENGTH`).

## 5. 평가 세트

검색 설정을 감이 아니라 숫자로 고르려면 "질문 → 정답" 묶음이 필요합니다. 컬렉션마다 평가 세트를 만들어 둡니다.

| 방법 | 내용 | 용도 |
|---|---|---|
| **LLM 생성** | 청크 세트에서 문서마다 골고루 지문을 골라, 지문마다 유형별 질문과 **근거 문장**을 만듭니다. 유형: 사실 확인 / 다른 표현(지문 단어를 피함) / 상황 설명형(사용자가 자기 상황을 말하며 묻는 질문) | 모델·청킹 비교의 기본 |
| **문장 추출** | 지문의 완결된 문장 하나를 그대로 질문으로 씁니다(표 조각·글자마다 띄운 제목은 건너뜀). LLM 이 필요 없지만 단어가 그대로 겹쳐 매우 쉽습니다 | 파이프라인 점검 |
| **직접 입력** | `질문 \| 정답 파일 이름 \| 근거 문장(선택)` 한 줄씩 | 실제 사용자 질문 — 가장 믿을 만함 |
| **가져오기** | 내보내기한 JSON(`{"items": [{"query", "doc_ids", "evidence"}]}`) | 다른 컬렉션·도구와 공유 |

- **정답 기록 방식**: 청크 id 는 청크 세트마다 달라지므로 쓰지 않습니다. 대신 **정답 문서**(doc_ids)와 **근거 문장**(evidence)을 남깁니다. 검색 결과 청크가 근거 문장의 글자 4-gram 중 60% 이상을 담고 있으면 "근거를 찾았다"고 봅니다. 그래서 청크 크기·겹침·경계가 다른 청크 세트도 같은 평가 세트로 비교할 수 있습니다. 근거 판정은 문서 id 와 상관없이 텍스트로 하므로, 같은 내용이 PDF·HWP 로 두 번 들어 있어도 어느 쪽을 찾든 정답입니다.
- LLM 이 근거를 원문과 조금 다르게 적으면 지문에서 가장 많이 겹치는 문장으로 바꾸고 "보정" 표시를 남깁니다.
- 같은 질문은 하나만 남기고, 질문과 근거의 **어휘 겹침**(글자 3-gram 자카드)을 계산합니다. 높을수록 키워드 검색에 유리한 쉬운 세트입니다.
- 만든 뒤 **검토**에서 이상한 질문을 체크 해제하고 저장하세요. LLM 호출 수와 입력·출력 토큰 수가 함께 기록됩니다.
- LLM 설정은 [llm.md](../../guides/llm.md) 를 보세요. OpenAI 호환 서버(Ollama 등 로컬 모델 포함)와 Claude API 를 쓸 수 있습니다.

## 6. 조합 평가

평가 세트 하나로 **청킹 × 임베딩 모델 × 검색 방식 × 리랭커** 조합을 한 번에 비교합니다(⑤ 평가 탭 아래, 최대 32개 조합).

- 고른 인덱스마다 의미·하이브리드, 그 인덱스들의 청크 세트마다 BM25, 그리고 각각 리랭커 없음/있음을 펼쳐서 실행합니다. 모든 조합은 상위 10개까지 검색합니다.
- **지표** (질문마다 계산해 평균):
  - `Hit@k` — 근거 문장을 담은 청크가 상위 k개 안에 있는가. 근거가 없는 질문은 정답 문서의 청크로 판정합니다.
  - `MRR@10`, `nDCG@10`(대표 지표) — 그 청크의 순위.
  - `문서 R@5` — 정답 문서가 상위 5개 **문서** 안에 있는가. 같은 문서의 청크는 한 번만 셉니다.
  - 평균·p95 검색 지연.
- **불확실성**: nDCG·Hit@5·MRR 의 95% 부트스트랩 구간(막대 위 검은 선)과, 1위와의 **짝지은 비교**(같은 질문들에서의 차이 → 유의한 차이 / 차이 불확실).
- **질문 유형별** nDCG(사실 확인·다른 표현·상황 설명형)와 **질문별 정답 순위표**를 함께 보여 줍니다. 순위표는 설정마다 결과가 다른 질문만 걸러 볼 수 있고, 칸에 마우스를 올리면 그 설정의 1위 결과가 보입니다.
- 결과는 실행 이력(`rag_eval`)에 저장되어 "이전 평가"에서 다시 볼 수 있습니다.

### 실측 — 공공문서 4건(약 29만 자), CPU

**직접 작성 24문항**: 원문과 다른 표현의 질문(사실 확인 6 · 다른 표현 12 · 상황 설명형 6)이며, 질문과 근거의 어휘 겹침은 0.053입니다.

| # | 설정 | nDCG@10 [95% 구간] | Hit@1 | Hit@5 | 문서 R@5 | 1위 대비 |
|---|---|---|---|---|---|---|
| 1 | 재귀 600/80 · KURE-v1 · 의미 | **89.9** [81.2, 97.9] | 79% | 100% | 100% | 기준 |
| 2 | 재귀 600/80 · BGE-M3 · 의미 | 88.4 [80.3, 95.6] | 75% | 96% | 100% | 차이 불확실 (p=0.81) |
| 3 | 재귀 600/80 · EmbeddingGemma 2 · 의미 | 87.4 [77.8, 95.4] | 71% | 96% | 100% | 차이 불확실 (p=0.62) |
| 4 | 재귀 600/80 · EmbeddingGemma 2 · 하이브리드 | 85.5 | 71% | 96% | 100% | 차이 불확실 |
| 5 | 재귀 600/80 · BGE-M3 · 하이브리드 | 82.9 | 67% | 96% | 100% | 차이 불확실 |
| 6 | 재귀 600/80 · KURE-v1 · 하이브리드 | 81.9 | 63% | 96% | 100% | 차이 불확실 (p=0.19) |
| 7 | 법률 800/0 · BM25 | 70.2 | 46% | 88% | 100% | 유의하게 낮음 (p=0.02) |
| 8 | 재귀 600/80 · BM25 | 69.6 | 54% | 83% | 100% | 유의하게 낮음 (p=0.02) |

> **정정 (2026-10-18)**: 처음 측정에서는 KURE-v1 이 nDCG 60.9 로 꼴찌였습니다. KURE 인덱스만 MariaDB 에 있었고, MariaDB HNSW 가 기본 탐색 폭에서 관세청 문서 청크 묶음을 통째로 놓친 탓이었습니다([검색 정확도 정책](#검색-정확도-정책-정확-검색--근사-검색)). 작은 인덱스는 정확 검색하도록 고친 뒤 다시 잰 값이 위 표입니다. 검색 지연은 저장소 · 동시 부하에 따라 달라 이 표에서 뺐습니다(의미 검색 0.1~0.5초, BM25 수 ms).

- **다른 표현** 질문에서 BM25 는 55~59 로 떨어지고, 의미 검색은 94(BGE-M3)~100(EmbeddingGemma 2)을 유지했습니다. 키워드가 겹치지 않는 실제 질문에서 임베딩의 가치가 드러납니다.
- 1~6위는 서로 "차이 불확실"입니다. 24문항으로는 KURE-v1 · BGE-M3 · EmbeddingGemma 2, 의미와 하이브리드의 우열을 가를 수 없습니다. 결정하려면 질문을 더 모으세요. EmbeddingGemma 2 는 모델이 가장 작고 빠릅니다.
- **문장 추출 57문항**(질문 = 원문 문장, 어휘 겹침 1.0)에서는 정반대로 BM25 가 nDCG 93.4 로 1위였고, 의미 검색은 69~79 였습니다(KURE 행은 MariaDB 수정 전 측정이라 제외). 원문을 그대로 베낀 질문으로 평가하면 키워드 검색을 과대평가합니다. 평가 세트는 실제 질문에 가깝게 만드세요.
- **리랭커**(Qwen3-Reranker-0.6B, CPU): 후보 30개 재정렬은 질문당 약 100초가 걸려 조합 평가에 넣기 어려웠고, 후보 10개로 줄여 따로 쟀습니다.

  | 설정 | nDCG@10 | Hit@1 | Hit@5 | 질문당 지연 |
  |---|---|---|---|---|
  | BGE-M3 · 의미 | 88.4 | 75% | 96% | 0.5초 |
  | BGE-M3 · 의미 + 리랭커(상위 10개) | 85.8 (차이 불확실, p=0.63) | 71% | **100%** | 22.6초 |
  | BM25 | 69.6 | 54% | 83% | 0.5ms |
  | BM25 + 리랭커(상위 10개) | 72.6 | 54% | 88% | 21.3초 |

  이 문서·질문에서는 리랭커가 순위를 뚜렷하게 올리지 못했고 CPU 지연이 매우 큽니다. 리랭커는 GPU 에서, 그리고 1단계 검색이 약할 때(BM25·짧은 질의) 효과를 확인하고 쓰세요.

## 7. 답변 생성 (RAG 테스트 → 답변 생성)

검색 결과를 근거로 LLM 이 답하고, 문장마다 근거 번호 `[n]` 을 인용합니다(`/rag/answer`). LLM 연결은 [llm.md](../../guides/llm.md) 를 보세요.

1. **검색**: 왼쪽에서 고른 검색 방식(의미 · BM25 · 하이브리드 + 리랭커)으로 상위 N개 청크(기본 5개, 최대 6,000자)를 고릅니다.
2. **답변**: 청크에 `[1]`, `[2]` 번호와 출처(파일 · 쪽 · 조문 제목)를 붙여 LLM 에 넘깁니다. 지시: 근거에 있는 내용만, 문장마다 근거 번호, 답이 없으면 "근거에서 찾을 수 없습니다". 답변은 **스트리밍**으로 한 글자씩 보입니다.
3. **검증** (답변이 끝나면 자동):
   - **잘못된 인용**: 근거 범위를 벗어난 번호.
   - **문장별 근거 포함률**: 답변 문장의 글자 3-gram 중 인용한 근거에 있는 비율. 50% 이상 "근거 있음", 25% 이상 "근거 약함", 그 밖은 "근거 없음"(환각 의심), 번호가 없으면 "인용 없음". 화면에서 문장 색으로 표시하고, 마우스를 올리면 수치가 나옵니다.
   - **LLM 판정**(선택): LLM 에 문장별로 근거가 뒷받침하는지 묻습니다. 작은 모델의 판정은 참고용입니다.
4. 시간은 **검색 · 근거 읽기(첫 글자까지) · 생성 속도**로 나눠 보여 줍니다. 로컬 소형 LLM 은 근거 2,000토큰을 읽는 데 20초 안팎이 걸립니다.

### 평가 세트로 답변 평가

같은 화면 아래에서 평가 세트 질문마다 검색 → 답변 → 검증을 일괄 실행합니다(작업). 근거 문장이 있는 질문은 검색 실패와 LLM 실패를 나눠 셉니다.

| 지표 | 뜻 |
|---|---|
| 답변률 | "찾을 수 없습니다"가 아닌 답의 비율 |
| 근거 검색률 | 근거 문장을 담은 청크가 LLM 에 전달된 비율 (검색 품질) |
| 정답 근거 인용률 | 답변이 그 청크를 실제로 인용한 비율 (LLM 품질). "검색됐을 때 인용"은 검색 성공한 질문만의 비율 |
| 문장 근거율 | 글자 기반 검증에서 "근거 있음" 문장의 평균 비율 |
| 지나친 거절 | 근거가 검색됐는데도 "찾을 수 없습니다"라고 한 비율 |
| 잘못된 인용 | 없는 근거 번호를 쓴 답변의 비율 |

실측 (공공문서 컬렉션 · 직접 작성 24문항 중 10문항, BGE-M3 하이브리드 근거 5개, 로컬 Gemma 4 E4B):

| 답변률 | 근거 검색률 | 정답 근거 인용률 | 문장 근거율 | 잘못된 인용 | 지나친 거절 | 질문당 시간 |
|---|---|---|---|---|---|---|
| 100% | 100% | 90% | 78.3% | 0% | 0% | 31초 |

- 정답 근거를 인용하지 않은 1문항("영어 약어")은 다른 근거의 줄임말 규정을 인용했습니다.
- 문장 근거율이 0% 로 나온 2문항은 실제로는 맞는 답이었습니다. 하나는 근거를 바꿔 말한 경우("'0'은 표기하지 않습니다"), 다른 하나는 원문 표기가 "1부 1실 7과 / 53명"처럼 끊겨 있던 경우입니다. **글자 기반 검증은 의역에 보수적**이므로, 낮게 나온 문장은 LLM 판정이나 사람 확인과 함께 보세요.
- 예산 질문에는 총액(95.4억 원) 대신 연도별 금액(20.7억 원)으로 답했습니다. 근거에 있는 숫자라 검증은 통과했지만 질문 의도와 어긋났습니다. 근거 인용만으로는 "맞는 답"을 보장하지 못합니다.

## 추천 출발점
