# 파인튜닝 테스트

범용 임베딩 모델을 **내 문서 분야에 맞게 추가 학습**하고, 같은 평가 세트로 학습 전후 검색 성능을 짝지어 비교합니다(메뉴 **파인튜닝 테스트**, `/finetune`).

## 왜 하는가

- 범용 임베딩 모델은 인터넷 · 위키 · 일반 질의응답으로 학습되어, 공문서 · 법령 · 사내 규정처럼 **용어와 문체가 특수한 분야**에서는 질문과 정답 지문을 충분히 가깝게 놓지 못할 수 있습니다.
- 원인은 대개 **분야 용어와 문체**입니다. 공문서의 "개의", "결재", "구매대행업자 등록부호" 같은 표현, 법령의 조문 구조, 사내 약어는 범용 학습 데이터에 드뭅니다. 사용자는 이런 용어를 다른 말로 묻습니다("회의가 성립하려면 몇 명이 와야 하나요?").
- 파인튜닝은 "이 분야에서는 이런 질문이 이런 지문과 같은 뜻"이라는 짝을 모델에 직접 보여 줘서, 질문과 정답 지문의 벡터를 가깝게 만듭니다. 모델 크기·검색 속도는 그대로입니다.
- 언제 효과가 큰가: 분야 용어가 많고(법률·의료·사내 규정), 질문이 문서와 다른 말로 들어오고, 범용 모델의 평가 점수가 낮을 때. 이미 점수가 높은 모델은 더 오를 여지가 적고(아래 실행 #1), 데이터가 나쁘면 오히려 떨어질 수 있으므로 **반드시 학습 전후를 같은 평가 세트로 비교**합니다.

## 어떻게 하는가

### 1. 학습 데이터 — (질문, 정답 지문) 쌍

컬렉션의 청크 세트에서 문서마다 골고루 지문을 뽑아 쌍을 만듭니다(`app/finetune/data.py`).

| 방법 | 질문 | 정답 지문 | 장단점 |
|---|---|---|---|
| **LLM 질문 생성** (권장) | LLM 이 지문을 읽고 만든 질문. 유형: 사실 확인 · 다른 표현(지문 단어를 피함) · 상황 설명형 | 그 지문 전체 | 실제 사용자 질문에 가장 가깝다. 로컬 LLM 은 지문당 20~30초 |
| **ICT** (Inverse Cloze Task) | 지문에서 고른 완결 문장 하나 | 그 문장을 **뺀** 나머지 | LLM 없이 즉시. 질문이 원문 문장이라 실제보다 쉽지만 분야 어휘에는 익숙해진다 |

- **누수 방지**: 비교에 쓰는 평가 세트(와 고른 평가 세트들)의 **근거 문장이 들어 있는 지문은 학습에서 뺍니다**(근거의 글자 4-gram 60% 이상 포함 시). 빼지 않으면 시험 문제로 공부한 셈이라 학습 후 점수가 실제보다 높게 나옵니다. 비교용 평가 세트는 자동으로 제외 목록에 들어갑니다.
- 같은 질문은 하나만 남깁니다. 학습 쌍은 모델 폴더의 `train_pairs.jsonl` 에 그대로 저장됩니다(재현용).

### 2. 학습 — 대조 학습 (MultipleNegativesRankingLoss)

sentence-transformers 의 `SentenceTransformerTrainer` 로 학습합니다(`app/finetune/trainer.py`).

- 한 배치에 쌍이 16개 있으면, 질문마다 자기 지문 1개는 정답, 나머지 15개 지문은 오답으로 보고 "정답과는 가깝게, 오답과는 멀게" 벡터를 조정합니다(in-batch negatives). 따로 오답을 만들 필요가 없어 데이터 만들기가 쉽습니다.
- **배치가 클수록** 오답이 많아져 효과가 좋지만 메모리를 많이 씁니다. *Cached 묶음 크기*를 지정하면 CachedMultipleNegativesRankingLoss 로 큰 배치를 작은 묶음으로 나눠 계산합니다(GradCache).
- 같은 지문이 한 배치에 두 번 들어가면 "오답"이 사실은 정답이 되므로 `NO_DUPLICATES` 샘플러로 막습니다.
- 모델에 정의된 **질의/문서 프롬프트**(예: EmbeddingGemma 의 `query`/`document`)를 학습에도 똑같이 붙입니다. 검색할 때와 학습할 때 입력 형식이 같아야 합니다.
- Matryoshka 모델은 *Matryoshka 손실*을 켜면 지정 차원들(예: 768·512·256·128)에서 동시에 학습해 차원을 줄여 써도 성능이 유지되게 합니다.
- 기본값: 1에폭 · 배치 16 · 학습률 2e-5 · 워밍업 10% · 최대 길이 512토큰. 학습률이 너무 크거나 에폭이 많으면 원래 능력을 잊어버립니다(catastrophic forgetting). 데이터가 수백 쌍이면 1~2에폭이 적당합니다.

### 3. 등록 · 비교 · 기록

1. 학습한 모델은 `data/finetuned/ft-{실행 번호}/` 에 저장되고, 원래 모델의 프롬프트·설정을 이어받아 카탈로그에 `파인튜닝` 태그로 등록됩니다(`source=finetuned`). 다른 모델처럼 인덱스 · 검색 · 벤치마크에 그대로 쓸 수 있습니다.
2. 평가 세트를 고르면, 같은 청크 세트에 원래 모델과 학습한 모델의 인덱스를 만들어(없을 때만) **의미 · 하이브리드 검색을 질문별로 짝지어 비교**합니다. 결과: nDCG@10 · Hit@1 · Hit@5 전후, 차이의 95% 부트스트랩 구간과 유의 여부, 순위가 바뀐 질문 목록.
3. **기록(모델 카드)**: 실행마다 `README.md` 를 모델 폴더에 남깁니다 — 원래 모델, 데이터 방법·규모·제외한 지문 수, 학습 설정, 손실 변화, 학습 전후 비교, 예시 학습 쌍. 화면의 *상세 → 기록*과 `GET /api/finetune/{id}/card` 로도 볼 수 있습니다.

### 주의

- CPU 학습은 느립니다. 0.5B 모델 · 수백 쌍 · 1에폭에 수 분~수십 분. 학습 중에는 앱에 올라간 다른 모델을 내려 메모리를 확보합니다.
- 멀티모달 모델의 텍스트 학습, LoRA 같은 부분 학습은 아직 지원하지 않습니다.
- 평가 세트가 작으면(수십 문항) 차이가 "불확실"로 나올 수 있습니다. 결론을 내리려면 평가 문항을 늘리세요.

### 실행 #1 · KURE-v1 × 공공문서 · ICT (2026-10-18) — 효과 없음, 측정 오류 발견

- **목적**: 한국어 검색 모델 KURE-v1(568M)을 공공문서 컬렉션(행정업무 운영 편람 · 국립국어원 업무계획 HWP/PDF · 관세청 보도자료, 약 29만 자)에 적응시키기.
- **데이터**: 청크 세트 "재귀 600/80"(576개)에서 150자 이상 지문 400개 → ICT 학습 쌍 378개(문서 4개). 평가 세트 "직접 작성 24문항"의 근거 문장이 든 지문 42개는 학습에서 제외.
- **학습**: MultipleNegativesRankingLoss · 1에폭 · 배치 16 · 학습률 2e-5 · 최대 256토큰 · CPU(Ryzen 7 7735U) 24단계 1,122초. 손실 1.079 → 0.518.
- **처음 결과 (잘못된 측정)**: 의미 검색 nDCG@10 60.9 → 90.2 (+29.2%p, 유의함). 원래 모델이 관세청 질문 6개를 모두 10위 밖으로 놓쳤다가 학습 후 1~2위로 찾은 것처럼 보였습니다.
- **검증**: 학습한 모델은 최대 256토큰으로 저장됐으므로 "입력 자르기 효과"를 가르려고 원래 모델을 sentence-transformers 로 직접 쟀더니, 원래 모델도 **89.9**(256토큰 90.1)였습니다. 원래 모델의 인덱스만 MariaDB 에 있었고, MariaDB HNSW 가 기본 탐색 폭에서 관세청 청크 묶음을 통째로 놓친 것이 원인이었습니다(상위 10개 재현율 0.792, 최소 0.00). 작은 인덱스는 정확 검색하도록 저장소를 고쳤습니다([rag.md 검색 정확도 정책](rag.md#검색-정확도-정책-정확-검색--근사-검색)).
- **다시 비교 (정확한 측정)**:

  | 검색 | nDCG@10 전 → 후 | Hit@1 | Hit@5 | 차이 (95% 구간) | 판정 |
  |---|---|---|---|---|---|
  | 의미 | 89.9 → 90.2 | 79.2 → 79.2 | 100 → 95.8 | +0.3%p [−6.1, +6.1] | 차이 불확실 (p=0.98) |
  | 하이브리드 | 81.9 → 81.1 | 62.5 → 62.5 | 95.8 → 95.8 | −0.8%p [−5.8, +4.7] | 차이 불확실 (p=0.74) |

- **결론**: 이 문서에서 KURE-v1 은 이미 Hit@5 100% 로, ICT 1에폭으로는 더 오를 여지가 없었습니다. 순위가 바뀐 7문항은 1~2계단씩 오르내렸을 뿐입니다.
- **교훈**: ① 학습 전후는 **같은 저장소 · 같은 검색 방식**으로 재야 하고, 놀랄 만큼 좋은 결과일수록 대조 실험으로 확인한다. ② 점수가 이미 높은 모델은 파인튜닝보다 평가 세트를 늘려 약점을 먼저 찾는다. ③ 저장소(근사 인덱스)의 오차가 모델 비교를 뒤집을 수 있다.

### 실행 #2 · Granite Embedding 97M × 공공문서 · ICT (2026-10-18) — 오히려 하락

- **목적**: 성능 여유가 있는 작은 다국어 모델(IBM Granite Embedding 97M Multilingual R2)에서 분야 적응 효과 보기.
- **데이터 · 학습**: 실행 #1 과 같은 ICT 학습 쌍 378개(같은 seed), 1에폭 · 배치 16 · 학습률 2e-5 · 최대 256토큰. CPU 24단계 **131초**, 손실 1.622 → 0.768.
- **결과**:

  | 검색 | nDCG@10 전 → 후 | Hit@1 | Hit@5 | 차이 (95% 구간) | 판정 |
  |---|---|---|---|---|---|
  | 의미 | 76.8 → 72.0 | 45.8 → 37.5 | 95.8 → 95.8 | −4.8%p [−13.6, +3.3] | 차이 불확실 (p=0.26) |
  | 하이브리드 | 80.3 → 78.2 | 58.3 → 54.2 | 95.8 → 95.8 | −2.0%p [−6.6, +1.6] | 차이 불확실 (p=0.31) |

- **해석**: ICT 의 "질문"은 문서 속 문장 그대로라서, 평가 세트의 자연스러운 질문(다른 표현 · 상황 설명형)과 모양이 다릅니다. 손실은 잘 내려갔지만(학습 데이터는 잘 맞춤) 실제 질문 형태에는 도움이 되지 않았고, 1위로 찾던 질문 일부를 2~5위로 밀어냈습니다. **학습 데이터의 질문 모양이 실제 질문과 비슷해야 합니다** — 다음 실행에서 LLM 질문 데이터로 비교합니다.
- **개선 사항**: 이 모델은 bfloat16 으로 저장되어 있어 처음에는 학습 코드가 bf16 그대로 불러왔고, bf16 을 하드웨어로 지원하지 않는 CPU 에서 단계마다 수 분이 걸렸습니다. 학습은 항상 fp32 가중치로 불러오고 GPU 가 bf16 을 지원할 때만 혼합 정밀도를 쓰도록 고쳤습니다(약 30배 빨라짐).

### 실행 #3 · Granite Embedding 97M × 공공문서 · LLM 질문 (2026-10-18) — 개선 없음

- **데이터**: 로컬 Gemma 4 E4B 가 지문 100개에서 질문 297개 생성(사실 확인 · 다른 표현 · 상황 설명형 각 99개, 실패 0, 입력 71,272 · 출력 29,078 토큰, 동시 2개로 약 55분). 평가 세트 근거가 든 지문 30개 제외. 예: "국어 사용자들이 언어를 더 편리하게 사용하도록 돕기 위해 국립국어원이 하는 일은 무엇인가요?"
- **학습**: 1에폭 · 배치 16 · 학습률 2e-5 · 최대 256토큰, CPU 19단계 85초, 손실 1.455 → 0.567.
- **결과**:

  | 검색 | nDCG@10 전 → 후 | Hit@1 | Hit@5 | 차이 (95% 구간) | 판정 |
  |---|---|---|---|---|---|
  | 의미 | 76.8 → 71.6 | 45.8 → 37.5 | 95.8 → 91.7 | −5.2%p [−14.8, +3.8] | 차이 불확실 (p=0.23) |
  | 하이브리드 | 80.3 → 77.5 | 58.3 → 54.2 | 95.8 → 95.8 | −2.7%p [−7.2, +0.6] | 차이 불확실 (p=0.17) |

- **해석**: 실제 질문 모양의 데이터로도 오르지 않았습니다. 가장 유력한 원인은 **거짓 오답(false negative)** 입니다. 문서가 4개뿐이라 한 배치(16쌍) 안의 다른 지문 대부분이 같은 문서의 비슷한 내용인데, MultipleNegativesRankingLoss 는 이들을 모두 "오답"으로 보고 밀어냅니다. 데이터가 300쌍 안팎으로 적고, 평가가 24문항이라 작은 변화를 가를 수 없는 것도 한계입니다.
