멀티모달 — 어디에, 어떻게

어디에: 파이프라인의 맨 앞(입력 · 임베딩 · 검색)과 맨 뒤(답변 생성 · 출력)
  • 멀티모달 임베딩 — 제품 사진으로 "이거랑 비슷한 매뉴얼 찾아줘": 이미지 자체를 벡터로 바꿔 관련 텍스트 · 이미지를 검색
  • 멀티모달 RAG — PDF 속 그래프 · 설계도를 글로 바꾸지 않고 이미지 청크 그대로 저장 · 검색
  • 멀티모달 답변 — 이미지 근거와 텍스트를 함께 비전 LLM 에 넣어, 글 외에 차트 · 음성까지

멀티에이전트 — 어디에, 어떻게

어디에: 질문을 받아 처리 과정을 설계하는 컨트롤 타워(라우터 자리)와 수행 단계 전체
  • 오케스트레이터 — "작년 분기별 매출 이미지 분석해서 보고서 쓰고 요약해 줘"를 쪼개 전문가에게 배정
  • 검색 전문가 — 사내 · 이미지 · 웹 검색만 전담, 부실하면 스스로 재검색(Self-RAG)
  • 분석 · 코딩 — 코드를 실행해 무결성 검증 · 통계
  • 품질 검증 — 원문 일치(환각) · 보안 규정 검사 후 반려 또는 통과

기반 실측에서 가져온 설계 원칙
  • 단계를 늘릴수록 단계마다 검증 — 작은 로컬 모델의 에이전트 답은 근거 밖 문장이 늘었습니다(판례 질문 문장 근거율 50% vs RAG 91%). 반대로 번호 조회처럼 도구 선택을 규칙으로 정해 주면 정확도가 크게 올랐습니다(조문 번호 질문 근거 인용 75% → 100%). 오케스트레이터는 정할 수 있는 것은 규칙으로, 나머지만 LLM 에 맡깁니다.
  • LLM 검증만 믿지 않는다 — 사람 판정 28개에서 작은 LLM 판정은 모두 '근거 있음'이었습니다. 검증 에이전트는 사람 판정으로 보정한 점수(근거 일치 · 질문 관련성)를 함께 씁니다.
  • 작성 모델은 난이도로 나눈다 — 소형 모델 E2B 는 지연 −21% 대신 품질 −13(유의). 짧은 정형 작성만 sLLM 으로.
  • 단순한 질문은 그대로 RAG 한 번 — 계획 · 분배 비용이 답변보다 클 수 있습니다. 단일 vs 멀티에이전트를 같은 질문으로 비교해 정합니다.
